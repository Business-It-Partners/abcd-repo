## Scope, page, and workflow

Internal module `patient-payments` at `finance/patient-payments`. Show the current outstanding-patient list and current-balance view. Finance users can switch between Received and Outstanding, open a patient's ledger/details, page to older ledger entries, and collect a payment and/or discount against the Worker-provided current balance. Reception access to the Finance app remains denied by existing M15 policy and is outside this integration scope. The page does not expose correction/reversal controls; the patient ledger correction routes used elsewhere are outside this sub-app.

## Business rules and permissions

- Report access requires `patient_payments.outstanding.read`. The Worker only returns received rows to actors with `patient_payments.received.read`; Reception does not have that capability and must not see received totals/rows.
- Ledger read requires `patient_billing_ledger.read`; collection requires `patient_payments.collect`. Current SaaS roles grant these to admin and Reception; doctors lack Finance payment access.
- Both payment and discount amounts are non-negative NPR with at most two decimals; their sum must be positive and cannot exceed the current Worker balance. Preserve the accepted payment methods and valid date restriction in the source UI/Worker contract. The Worker writes the receipt and ledger; never calculate the authoritative due locally.
- Collection is an idempotent financial write. Retain the original operation key on unknown outcomes. Worker validation, role checks, clinic scoping, receipt numbering, ledger update, and audit remain authoritative.

## API requirements

- `GET /v1/patient-payments?from=…&to=…` returns outstanding and received report data; the host route requires `patient_payments.outstanding.read` and permits only `from`/`to`.
- `GET /v1/patients/:id/ledger?month=…&cursor=…` requires `patient_billing_ledger.read`. Use the server cursor for older ledger entries.
- `POST /v1/patients/:id/payments` requires `patient_payments.collect` and the SDK idempotency key. It records a payment; do not use the broader patient ledger correct/reverse endpoints here.
- The report is a full response, not paginated. The visible SaaS month filter is applied to the report rows in the client; use the supported period query when loading a month and account for the 256 KiB SDK response limit.

## Implementation notes

The implementation is limited to this child and preserves M17.7.1 Transaction Record in the same `company.dental.finance.m17` app package. The Finance module catalogue now contains `transaction-record` and `patient-payments`; no Patient Payments app ID or Store listing was added. The app manifest and package are both `1.1.0`.

The Patient payments page follows the pinned SaaS hierarchy and labels: Bikram Sambat month/all-month filter, capability-filtered Received and Outstanding tabs, outstanding-patient actions, patient identity and ledger summary, account-activity table, cursor-based older-entry action, and the payment/discount modal with payment date, method, NPR amount, discount and resulting-due preview. Ledger values and the current balance come from the Worker. Collection requires a freshly loaded ledger, obeys non-negative two-decimal NPR/date/method/current-due rules in the UI, and still relies on Worker validation and audit for authority. No correction or reversal workflow was added.

`GET /v1/patient-payments?from=…&to=…`, `GET /v1/patients/:id/ledger?cursor=…`, and `POST /v1/patients/:id/payments` use the existing Finance `ClinicClient` routes. A POST is represented by one SDK `ClinicCommand`; an unknown response leaves the original immutable payload and operation key in memory and offers retry of that same command. A definitive stale-balance conflict refreshes the ledger and keeps the form available for review. There is no app-owned HTTP, authentication, local authoritative store, or offline write queue.
