## Source-derived behavior

An open-case Work Entry screen holds plan, chart, canal, prescription, lab, follow-up, payment, note and case-disposition changes as one draft. `POST /v1/work-entry/commit` submits these together with the expected case row version and one idempotency key. The Worker validates and resolves dependent identifiers, checks `work_entry.access` and any payment capability, then batches the business mutations. Media byte transfers have a separate lifecycle.

Separate create/update/cancel/status operations remain separate only where the SaaS source already defines separate commands. After an unknown commit result, the app must retain the original immutable `ClinicCommand`, block another commit, offer same-key reconciliation and refresh persisted case state after a confirmed result.
