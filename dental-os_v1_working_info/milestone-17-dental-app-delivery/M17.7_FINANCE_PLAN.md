## Product and architecture contract

Finance is one top-level first-party Dental OS app. The app package uses one signed app identity and the M13 trusted module catalogue/explorer model: one parent app window, eight internal module IDs, a shared Finance toolbar, and capability-filtered module choices. Selecting a sub-app changes the content in that window. This follows [M13](../milestone-13-first-party-app-shells/PLAN.md), the [V1 runtime and package architecture](../../dental-os_v1-documentation/07_V1_APP_RUNTIME_AND_ISOLATION.md), and the [repository structure](../00_REPOSITORY_STRUCTURE.md).

Create the future app under `apps/dental-apps/company.dental.finance.m17/`, reusing the existing Finance artwork. The package will declare one supported family, `clinic.app.finance`, plus the normal SDK operations needed for brokered clinic API access and session context. All API calls go through the Dental OS SDK/API broker. The SaaS Worker remains authoritative for clinic scope, permissions, validation, ledger projections, writes, and audit. Do not copy SaaS server, authentication, Firebase, or HTTP transport code into the app. Do not add local authoritative finance data, computed balances, or an offline write queue.

The exact M17 app ID `company.dental.finance.m17` did not occur in the base repository. The old `company.dental.finance` M13 preview package and its sequence-30 staging cleanup are historical records; do not reuse or relabel that ID or its version history.

### Important page, error, empty, loading, and modal states

- All eight areas use the clinic page loading/refresh presentation. Module loading, page refresh, and any write-in-progress state must remain visible and must not imply that an uncertain write was cancelled.
- Transaction Record begins in a loading state, converts the selected Bikram Sambat month into an AD inclusive range, reports invalid ranges or failed report loads, and shows the report's empty-period state. Keep Worker totals and overview values separate from any displayed row list.
- Patient payments distinguishes the admin Received and Outstanding tabs from Reception's Outstanding-only view. It has received-month and outstanding-empty states, report errors, a patient ledger/details modal, cursor-based older-ledger loading, and a collection modal with current-balance loading, form validation, save state, and recoverable API errors. The Worker filters received rows for users without `patient_payments.received.read`.
- General Expenses and Salary Payments share `FinanceView` list, clinic-month/all-month filtering, no-records state, data-load error, Add/Edit/Correction modal, validation/save error, and reason-required void confirmation. Salary adds a separate active-staff load and salary-month selection.
- Product List distinguishes an empty catalogue from no search matches; it has catalogue-load errors, add/edit form errors, a full-page product detail view (`ProductDrawer`), pending active-status toggle, and update failure feedback.
- Purchases distinguishes no invoices from no filter matches, has list-load error and month/search filters, a staged form/review flow, validation and duplicate-invoice risk warnings, a purchase details modal, correction reason, and reason-required void confirmation. A failed save keeps the review available for retry.
- Supplier List has list-load and detail-loading states, no-suppliers/no-filter-match states, supplier add/edit modal validation, app-window detail/back navigation, statement data, and payment entry from the detail view. If the statement cannot load, Dental OS must show the failure and withhold authoritative balance/statement values; do not copy SaaS's client-side fallback arithmetic as an authority.
- Supplier Payments has a month/all-month filter, loading/error/empty states, record/edit payment modal with supplier and optional invoice association, correction reason, and a busy reason-required void confirmation.
- All API validation, permission, conflict, connectivity, maintenance, and unknown-write results need visible, actionable states. A lost response must retain the original operation ID/idempotency key for same-command reconciliation. Do not turn a timeout into a second financial write.

### Finance app-window page history

Use the SDK's existing `ClinicClient.createHistory` / `AppHistory` contract for history within the active Finance sub-app. Selecting a different Finance module through `onModuleSelected` resets the stack to that module's main page; Finance module switches are not Back/Forward entries. Product List and Supplier List are the only current main/detail page flows: opening a product or supplier pushes its detail page, and Back returns to the same sub-app's list. Route data and business IDs remain in Finance; the OS receives only opaque history entry UUIDs.

Patient ledger, purchase details, supplier purchase/payment details, forms, edits and confirmations remain dialogs and do not create page-history entries. Keep their dirty/modal/pending-write guards active. Do not use browser `window.history`, URL fragments or `popstate` for Finance app-window page navigation.

## Exact shared SDK/platform and API gaps

1. **Reception is blocked at the parent Finance-family gate.** At the required base, `electron/sdk/appPolicy.ts` declares `clinic.app.finance` with `finance.manage`/`patient_payments.outstanding.read` but `excludedRoles: ['reception']`. The historical M13 Finance metadata also excludes Reception globally. The host already validates trusted per-module capability labels and filters modules by the session capabilities. Reception access is explicitly deferred by the user for this source implementation; no host policy was changed or bypassed. Before Reception can use the Finance package, a later integration must remove the global exclusion and provide trusted module metadata that gives Reception only `patient-payments` (visibility capability `patient_payments.outstanding.read`), while all other modules require `finance.manage`. Keep one `clinic.app.finance` family and one app ID. Do not add the separate `clinic.app.patient-payments` family/package back into Finance.
2. **Finance route rules already exist.** At the required base, `electron/sdk/clinicRoutes.ts` contains Finance-family rules for all listed Finance endpoints and the patient-payment report, ledger, and collection routes. The signed Finance release still needs the exact format-2 `clinic.api.request` grant and the package must keep Worker capability checks. No per-ID route rule or new business route is needed for the listed contract.
3. **Finance list responses are not server-paginated.** The pinned list API clients accept no cursor/limit for expenses, salaries, products, purchases, suppliers, supplier payments, transaction reports, or the patient-payment report. The patient ledger alone supports a cursor. The current `usePaged…` hooks mostly return the full Worker array with `hasMore: false`; they do not make these list APIs bounded. The SDK JSON broker accepts at most 256 KiB of response JSON and 12 KiB of request JSON. Keep report date ranges where available, never derive authoritative totals from a partial list, and establish a verified dataset/response budget or a reviewed SaaS/API pagination change before claiming unbounded history support. If a valid purchase or other write can exceed the SDK request limit, stop and version the supported contract rather than bypassing the SDK.
4. **Supplier, supplier-statement, purchase, and supplier-payment responses are unpaginated.** The selected Supplier list child uses those full Worker responses for its directory, statement, purchases tab, and detail/payment form. The SDK's 256 KiB response ceiling is already documented above; do not claim unbounded history support until a verified budget or reviewed pagination contract exists.
5. **Unknown write receipt recovery is app-session scoped.** `ClinicClient.command` retains an immutable payload and idempotency key for retry while the app remains mounted, but the shared host SDK has no operation-receipt lookup to reconcile a pending supplier, purchase, or payment write after the app view or session is replaced. Keep the command open for same-key retry while mounted and do not claim recovery after process/session replacement.
6. **Purchase request sizes can exceed the SDK contract.** The Worker permits up to 100 lines and up to 200 characters per item name (plus units, notes, invoice and other fields); the SDK caps a JSON business request body at 12,000 bytes. The Purchases form measures the serialized request and blocks larger writes without splitting the invoice. Some Worker-valid invoices therefore remain unavailable until a reviewed SDK/API size-contract change.
7. **The M17.8 standalone plan overlaps this SaaS sub-app.** The current Finance Patient payments page already covers the Reception outstanding worklist, ledger details, and collection. Its scope is now M17.7.2 inside the one Finance app; M17.8 is retained only as a superseded-plan pointer and will not create a separate package, ID, Store listing, or version sequence.
