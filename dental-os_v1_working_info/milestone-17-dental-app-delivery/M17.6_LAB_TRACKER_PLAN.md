## App scope

Build both same-package modules from scratch against the maintained Dental SaaS UI/API reference at `desktop/fewa_demo/dental-saas`. Pin the source revision and use the current Dental OS shared UI package and SDK. Implement the app UI and workflows while keeping platform transport in the supported SDK:

- **Lab Tracker:** order/request list and detail, assignment, status progression, receive/fit confirmation, notes, and audited cancellation as supported by SaaS.
- **Lab Supplier Record:** supplier directory, add/edit/status, supplier history, and links to lab orders where supported by SaaS.

The implementation imports the SaaS Lab Tracker, supplier directory, supplier history and month picker UI. Its Dental OS adapter uses `ClinicClient` reads and idempotent commands. The two modules stay in one package and retain separate view state while switching. The existing M15 route family already permits these clinic operations; no new app-ID host policy is needed.

### Contract decisions

- Lab requests start in `pending_assignment` and are assigned with `POST /v1/lab-orders/:id/assign`. The assignment includes supplier, work label, tooth, shade, sent date, reception note, and expected row version.
- Status progression uses `PATCH /v1/lab-orders/:id` with `expectedRowVersion`; the Worker supplies `receivedOn`/`fittedOn` when needed. A sent order may return to pending with `clearAssignment: true`.
- Doctor-submitted procedure, tooth, shade, and clinical note remain read-only. Reception note is a separate editable field.
- Cancellation is an audited status update with its reason in `receptionNote`. Only sent and received orders can be cancelled; cancelled orders remain visible in history and cannot be restored. Pending and fitted rows do not offer cancellation.
- Lab suppliers remain in the shared Finance supplier directory. New records are lab-only. `lab_tracker.access` users can edit lab-only suppliers; editing a `both` supplier requires `finance.manage`.
- Supplier detail shows contact information and related lab order history only. It does not expose statements, balances, or payments.
- Conflicts refresh the rows. An uncertain result retains the original command and idempotency key for a same-command retry. No local authoritative business database or offline write queue is added.

### App-window page history

The `lab-suppliers` module's supplier directory and supplier work-history detail page use `ClinicClient.createHistory` / `AppHistory`. OS Back and Forward switch between that module's list and selected supplier detail. Selecting the other Lab Tracker module resets the history root to its main page; module switching itself is not a history entry. The Lab Tracker module's order detail remains a drawer/sheet, so it stays local and does not create an OS page-history entry. Filters and tabs remain module view state.
