# M17.2 Plan — Patient Record

**Status:** PLANNED — next fresh implementation after M17.3 Appointments, in the user-directed execution order.
**Historical preview ID:** `company.dental.patient-record` (its staging release was removed at sequence 30; local historical records remain).
**M17 release ID/version:** New unique ID to assign before implementation; first release under that ID is `1.0.0`.

## App scope

Build from scratch the patient search/list, registration/intake, patient detail and longitudinal clinical records, corrections, and other source-defined patient-record workflows. Use `desktop/fewa_demo/dental-saas` for the UI/workflow/API reference, pin the exact SaaS source before implementation, and recreate the Dental OS app UI using the current shared UI package and SDK. Build the app UI from the maintained Dental SaaS reference; do not copy SaaS server or transport code. Preserve the source behavior and present truthful loading, empty, error, conflict, and recovery states.

## SDK and acceptance focus

- Derive every method, route, query, role, and payload limit from current Dental SaaS source and the supported Dental OS SDK contract. Use only the SDK broker for business APIs.
- Verify patient/clinic scope, permitted clinical roles, denial cases, audit/refresh behavior, stable write keys, unknown-outcome reconciliation, and stale-record conflicts using synthetic staging data.
- Integrate X-ray selection, upload, readback, and display through the existing M15 media SDK and host path. Do not implement app-owned network transfer, signed-URL handling, or a parallel media API.
- Verify that the app can only see the current authorized clinic's permitted records/files. Do not add file withdrawal, retention, or deletion behavior; SaaS owns that lifecycle.
- Verify multi-step intake/correction drafts, dirty-form decisions, bounded payloads, keyboard/focus, and managed-window behavior.

M17.2 may implement against the current M15 contract while M15 closeout continues. Mark media proof provisional until the M15 media exit is clean and repeat the affected integration cases on the final M15 source before G14 closure.

## Release identity and acceptance sequence

Use the new M17 staging signer after its public key is pinned in the staging verifier. Keep its private key local-only in the protected, Git-ignored `signing/` area until moved to the user's vault. The new signer is separate from the clinic credential used for synthetic staging acceptance. Verify X-ray paths with the current M15 SDK; do not add SaaS-owned file withdrawal, retention, or deletion behavior. Run the focused local Linux checks first; Windows-device verification and independent review remain separate gates.
