## Current SaaS API contract reviewed

Source pin: Dental SaaS `f0d059d36540b4b6907cace089085ce0df62d454`. Exact reviewed source files and blob hashes are recorded in [SOURCE_IMPORT.json](../../apps/dental-apps/company.dental.appointments/SOURCE_IMPORT.json).

| Operation | Route | Contract used by the app |
| --- | --- | --- |
| Day schedule | `GET /v1/appointments?date=YYYY-MM-DD[&doctorName=…]` | Date-only clinic-local day; doctor filter is optional |
| Range schedule | `GET /v1/appointments?bucket=today\|week\|upcoming\|cancelled&today=YYYY-MM-DD[&doctorName=…]` | Worker defines the range and returns no more than its bounded appointment response |
| Summary | `GET /v1/appointments/summary?today=YYYY-MM-DD` | Returns `todayBooked`, `thisWeekBooked`, `upcomingBooked`, and `cancelled` |
| Doctor references | `GET /v1/clinic/staff-references` | App selects active rows whose `staffType` is `doctor` |
| Book | `POST /v1/appointments` | Name, optional phone, doctor name, date, start minute, duration and reason; `Idempotency-Key` is host-mediated |
| Reschedule/edit | `PATCH /v1/appointments/:id` | Full appointment fields plus `expectedRowVersion`; only active doctors may be selected |
| Status | `POST /v1/appointments/:id/status` | One of `booked`, `arrived`, `cancelled`, `no_show`, plus `expectedRowVersion` |

The SaaS Worker authenticates clinic access and owns branch-scoped appointment data, active-doctor validation, overlap detection, row-version conflicts, status persistence, and idempotency receipts. At the pinned source revision, the Appointments controller does not call `requireClinicCapability("appointments.access")`; the current SaaS role map grants this capability to admin, doctor, and reception. The app and Dental OS broker enforce the signed app/module and session-capability checks, but a future restriction by role would also need Worker enforcement. Record that boundary; do not claim the Worker independently denies a role. The UI's same-doctor overlap warning uses only the currently loaded list and is advisory; every write is checked by the Worker. Dates remain ISO date-only values, and “today” is derived using the clinic session timezone.

## SDK and acceptance focus

- Every read and write uses `ClinicClient` and the `clinic.api.request` SDK route. No direct HTTP, bearer token, local authoritative data, patient-record lookup, or offline queue.
- Verify day/range boundaries, doctor filtering, active and inactive doctor behavior, empty/loading/error states, create, reschedule, every permitted status, conflict and stale revision handling, and server overlap rejection.
- Verify unknown write recovery by retrying the same immutable command with the same operation identity, then refresh and confirm one saved booking.
- Verify the signed app/session-capability gate and tenant scope; record the current Worker role-guard gap, then verify server-side role denial only after the SaaS route enforces or otherwise proves it. Verify session change clears rendered clinic data and no call occurs after revocation.
- Verify unsaved booking protection, keyboard/focus behavior, narrow managed-window layout, and a signed package opened from the Store.
- Use only authorized synthetic staging entries; record cleanup that SaaS permits. Never create real patient records as appointment stubs.

## M17.1 fixture lessons applied

The M17.1 private staging attempts exposed harness timing and selector problems: the Store menu was collapsed, session identity resolved asynchronously, and an SVG selector did not identify the intended control. A separate launch-feedback regression also needed its fixture clock corrected. These were harness issues, not evidence of SaaS credential or package failure. M17.3 waits for the app's rendered readiness state, drives controls by accessible names/roles, and computes synthetic clinic dates in `Asia/Kathmandu`; its fixture does not depend on a fixed machine date or artwork selector. M17.3's early fixture attempts then caught an ambiguous nested time-control label and a save-confirmation message cleared during refresh; after those were corrected, the fixture exposed the retry button being covered by the open booking modal. The UI now keeps the original intent actionable in the modal and disables further edits until reconciliation. Failed attempts remain in the timestamped artifacts; the later 20-check pass supersedes them.
