## Implemented locally

- Recreated the SaaS Staff directory layout, roster table, search/type filters, status and salary columns, empty state, add-staff modal, staff profile, profile summary/edit form, work history, and salary history using Dental OS shared UI and the source styles' visual direction.
- Preserved SaaS Staff fields and type/status labels; directory and profile data come from the existing clinic API through `ClinicClient`.
- Creates and updates use SDK commands with stable idempotency. Profile updates include `expectedRowVersion`; conflicts retain the draft, fetch the latest server version, and offer an explicit reload. Unknown write outcomes retain the original command for retry and block another write until the original resolves.
- Work history is shown for doctor profiles and uses the SaaS date-range behavior and month picker. Other staff types receive the source explanation. Clinical-stage value remains labeled as clinical work value, not salary or commission.
- Salary history is requested only when the session grants `finance.manage`; without that capability the tab and request are absent. The response is filtered to the current staff profile; recorded and voided entries remain visible, while totals count recorded entries only.
- Added the private Staff document register, upload, read/preview and withdrawal flows required by M17.9. Listing and withdrawal use the existing Staff API routes. File reading and upload transfer use only M15 `clinic.media.read` / `clinic.media.upload`, with typed `staff_document` identity, bounded file type/size, host-owned transfer, and host-verified metadata/content. The app contains no direct credentials, signed URL, cloud request, or server transport code.
- Session loss returns to a blocked status screen. Shared window lifecycle reports dirty forms and open modals; navigation asks before discarding edits. App access is denied unless the clinic session grants `staff.manage`.
- The current SaaS source temporarily sets `privateDocumentsVisible = false`. M17.9 explicitly calls for the M15 media SDK/host transfer, so the Dental OS implementation follows that plan and keeps document access gated on exact release media grants.

## Access contract and remaining gates

The precise route, family, and permission matrix is in the package [`API_CONTRACT.md`](../../apps/dental-apps/company.dental.staff.m17/API_CONTRACT.md). The host route table and Worker currently support the Staff read/write/history routes. `staff.manage` gates the app, directory, profile, edits, clinical work, document listing and withdrawal; the current Worker role map grants it only to admin. `/v1/clinic/salary-payouts` separately requires `finance.manage`; the current role map grants that only to admin as well.

The package is not signed, so exact release operation grants for `clinic.media.read` and `clinic.media.upload` have not been issued. File open and upload remain safely blocked until those exact grants are granted and verified. No permission was broadened to bypass the role or host policy. The current Staff Worker does not implement the `/v1/clinic/staff/:staffId/documents/:documentId/abort` route called by M15 host cancellation after remote commit begins. The app therefore permits local cancellation before commit, disables cancel after commit starts, and asks for retry of the same transfer to resolve an uncertain commit. Adding a Worker abort route is outside this app-only scope. Existing M15 evidence demonstrates host-level Staff media bounds and cross-clinic denial, but this app has not yet undergone M17.9 clinic isolation or workflow acceptance.
