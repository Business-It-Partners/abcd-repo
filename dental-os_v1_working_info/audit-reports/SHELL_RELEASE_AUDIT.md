## App-development baseline versus release work

For M14 app development, a frozen commercial host matrix and signed platform updater are not prerequisites to author app UI or run current private Linux/runtime and app CI. The prerequisites for **integrated app acceptance** are the existing trusted session, verified isolated package/SDK, Store staging path, shell/module handoff and resolution of the app-to-platform dependencies below. For continued staging-feed use, assign an operator and rehearse higher-sequence metadata-only renewal plus expiry/recovery; that is separate from production platform signing/updater work. M20's full external install/update/operations promises are release work; they should not be pulled into the app implementation task by implication. M20 plan currently lists M12/G12 and M14 as dependencies, so the lead should resolve which M20 planning work can begin before gates close versus which G20 acceptance must wait.

The M14 platform dependency register at `codex/milestone-14` SHA `48c18401cada192bfa0bea02a4afdd0cb10e45ca` adds three concrete platform implications:

- **P09:** Staff private upload/download needs a host-mediated document-intent/PUT/finalize/download flow; the SaaS bearer-token `fetch` must not be reused by app renderers. Prove MIME/size/checksum, authorization, tenant isolation, error cleanup and secret isolation. Coordinate with existing 10 MiB Worker upload vs 8 MiB broker blob-read design.
- **P10:** patient/case links across apps need an authorized inter-app navigation/selection contract that preserves dirty/modal state, checks destination capability and avoids sensitive URL state.
- **P11:** measure sanitized app payloads against current SDK caps (12,000-char JSON body, 16 KiB envelope, 256 KiB response, 8 MiB blob read); use pagination/chunking or reviewed versioned changes rather than silently relaxing limits.

These are platform-team dependencies for integrated functional acceptance; app work may progress with explicit test-only mocks as the M14 handoff states. The dependency register also records P08: a Windows dock-edge visibility failure at `263b8754` / Actions run `39632562459`, followed by a pass at `41c88796` / run `39634626258` without a runtime change. Preserve both and assess reliability during platform reconciliation; the later pass does not erase the intermittent failure.
