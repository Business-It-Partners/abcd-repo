## Contract boundaries for M15.2/M15.5

The M14 dependency register at `codex/milestone-14` source `48c18401cada192bfa0bea02a4afdd0cb10e45ca` informed the original scope. Final M15 disposition is limited to declared platform capabilities; M14 app implementation/public release acceptance remains separate:

- **API authority:** the host keeps family-scoped route/session policy and does not register clinic APIs by app ID. Each package selects exactly one supported `clinic.app.*` family. Fresh signed metadata and an exact format-2 release grant authorize the new company ID/version/package; the unchanged host enforces the existing routes, app role, extra Worker capabilities and session state. New routes, families, operations or native capabilities still need a platform update.
- **Private media:** bounded host-mediated reads are implemented and verified. The local SessionManager gates the Patient Record/patient-media and Staff/staff-document family pairs under clinic permissions; any approved ID selecting one of those families is still subject to the exact signed grant. A private staging Dock fixture uploaded/read back a real JPEG and withdrew its record. A separate real staging acceptance passed both SaaS size caps and readback, cap-plus-one rejection before credentials/network, same-clinic fresh-session recovery after a lost patient content response, and Staff finalise-response reconciliation. A two-clinic negative test denied synthetic record and withdrawn-media reads and rejected both upload intents before bytes. A follow-up 19-check staging probe confirmed Clinic B's signed Patient Record and Staff apps receive `ACCESS_DENIED` for Clinic A's exact synthetic image and document while each file is active; each metadata route returned 404, no binary request was dispatched and zero bytes were returned. See the dated media evidence in `VERIFICATION_EVIDENCE.md`. The targeted MIME/checksum, session-revocation and server receipt-race scenario outcomes passed, but a clean corrected verifier run remains unverified; the M15 media-platform exit is incomplete. See [consolidated media staging acceptance](evidence/P07_MEDIA_STAGING_ACCEPTANCE_2026-10-22.md). SaaS-owned file retention/deletion is outside the OS release gate; no public media grant exists.
- **Cross-app links:** no cross-app navigation capability is granted. Any later patient/case navigation need requires a separate ADR and must preserve dirty/modal work, independently authorize the destination, handle absent/denied destinations, and keep identifiers out of sensitive URL state. R13 remains in force.
- **Payload budgets:** measure sanitized M14 app cases against the current 12,000-character JSON body, 16 KiB request envelope, 256 KiB response, and 8 MiB blob-read bounds. Prefer measured pagination/chunking or an explicitly versioned approved change; never silently raise caps.
- **Print/export:** decide only from a concrete V1 app inventory and host constraints. The current unavailable adapter is not permission to invent an app-to-host escape path.

No route-manifest format is used. The host keeps its closed route and session policy, but selects that policy from exactly one supported `clinic.app.*` capability in the verified package instead of a compiled per-app-ID map. A new company ID can use an existing family and route through signed package/catalogue/update-policy metadata and an exact format-2 release grant without changing the OS binary. A new app family, host route, API operation, media kind, or native capability still requires a platform compatibility review and implementation. M17 owns app UI and workflow adapters; platform authority stays in the trusted host/broker and SDK.
