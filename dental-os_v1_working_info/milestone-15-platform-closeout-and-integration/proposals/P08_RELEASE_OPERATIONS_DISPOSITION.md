## Current authority and invariants

- The staging catalogue and update policy are separate canonical signed metadata envelopes. The catalogue is wire `format: 1`; the update policy accepts wire formats `1` and `2`. Format 2 may carry exact per-release API-operation grant records under ADR-026. Each envelope is verified against its existing pinned staging trust key and purpose-specific Ed25519 signature. Neither control can introduce a publisher or key outside the platform trust configuration.
- Each control has its own positive monotonic sequence and freshness watermark. Renewal must use a strictly higher sequence for **both** controls than the current published and highest known/observed values. Reusing a sequence, lowering a sequence, changing bytes at an already observed sequence, clearing a watermark, or trusting an old cached envelope is not recovery.
- `issuedAt`/`expiresAt` must satisfy the current clock checks and a maximum lifetime of 24 hours. Expired metadata blocks unsafe launches and new distribution operations; it does not authorize offline bypass. Authenticated server time and the local clock are both checked. Do not extend expiry or relax skew/replay validation to make a drill pass.
- Keep every signed catalogue release row and update-policy app rule semantically unchanged for a metadata-only renewal: IDs, versions, object keys, package hashes/byte counts, payload digests, API format-2 per-release `{version, packageSha256, payloadDigest, apiOperations}` records, app capability ceilings, minimum versions, revocations and rollback controls. These signed grants remain bounded by the platform-pinned company trust ceiling. A grant, release, key or rollback change is a separately reviewed publication, not a renewal.
- Package-registry **format 2** is local install state, not the catalogue/update-policy wire format. It tracks immutable package digests and active/pending/known-good/trial state, with no more than three retained versions per app and no more than three quarantined failed digests. Eviction may remove only an unleased version outside active/pending/known-good/trial protection. Renewal must not invoke install, update, trim, rollback, registry repair or pointer migration.
- Release package objects are immutable. A metadata-only operation must not rebuild or upload `.dentalpkg` bytes. It updates only the authorized staging catalogue and update-policy metadata objects, with the existing conditional pointer/ETag safeguards. Local package bytes and format-2 registry pointers are invariants to capture and compare in the drill.

## Staging metadata renewal and expiry-recovery drill

This is a **proposed M15.5 procedure**, not an operation performed by P08. The source audit found no standalone metadata-only renewal tool. Before marking the drill repeatable, M15.5 must provide/review a preparation path that can re-sign the existing metadata without rebuilding or writing packages. If the current approved tooling cannot do that, record the tool gap and resolve it within M15.5; do not claim a successful drill by rebuilding packages.

### Routine renewal

1. **Assign people and scope.** Record the named staging operator and a second platform reviewer before the drill. The operator uses only the existing externally protected staging signing material and explicitly scoped staging publisher. The reviewer checks the metadata diff and target. Keep keys, credentials and secret values out of the checkout and evidence.
2. **Capture the pre-state read-only.** From the verified staging feed, record catalogue and update-policy sequence, issue/expiry times, canonical-envelope hashes, ETags, and the exact release/grant and policy/app-rule inventories, including any format-2 API grants. Record hashes and byte counts for the referenced immutable package objects. In a disposable private test profile, record package-registry format-2 digest list and active/pending/known-good/trial pointers for the synthetic test app. Do not read or alter the user's live profile.
3. **Prepare metadata only.** Copy the current release rows and app rules without semantic edits. Set new issue/expiry times within the 24-hour maximum and choose a strictly higher sequence independently for catalogue and policy, above the published and known watermark values. Sign each envelope with its already pinned, purpose-authorized staging key. Do not rotate/revoke keys or change grants in this procedure. If the latest sequence/watermark cannot be established, stop for reviewed recovery; never reset it.
4. **Validate before publication.** Verify canonical bytes, signatures, key purpose, staging environment/channel, server/local clock policy, expiry, monotonicity, package hashes/byte counts, all per-release and per-app grants (including exact API operation records under format 2), and exact semantic equality of release rows and policy rules against the pre-state. Reviewer approval is required before any staging pointer write. A difference beyond sequence/times/signatures is a different release/policy change and leaves this renewal procedure.
5. **Publish staging metadata only.** Under the staging-only authorization and existing conditional ETag/sequence guard, advance the catalogue and update-policy metadata pointers. Do not write, overwrite or delete any `releases/<id>/<version>/<wire-sha256>.dentalpkg` object; do not modify a desktop registry. If one metadata pointer advances and the other fails, stop and repair with a still-higher sequence; do not replay an older envelope or force an overwrite.
6. **Read back and compare.** Re-fetch the two public metadata envelopes, verify signatures and fresh sequence/expiry, and compare their release rows/grant rules with the approved pre-state. For format-2 policy, confirm the exact API operation grants are byte-semantically unchanged. Re-hash package objects and confirm byte counts are unchanged. In the private profile, refresh metadata and confirm the same installed digest remains selected; compare local registry format-2 active/pending/known-good/trial and retained-version pointers before and after. No app install, package rebuild or update should be needed.

### Expiry-recovery exercise

1. Use the disposable private profile and synthetic package only. With a controlled test clock or isolated expired-metadata fixture, prove that expired catalogue/policy data blocks the next unsafe launch/distribution action while preserving package bytes and registry state. Do not expire or tamper with the user's live metadata/profile.
2. Recover through the routine process: publish only newly signed staging metadata with sequences higher than all observed values and a fresh validity window no longer than 24 hours. The app's normal verifier must accept it with current authenticated server time; no watermark reset, stale-cache exception, rollback to an older envelope or alternate trust root is allowed.
3. Re-fetch under the private profile. Confirm the same already installed, authorized, known-good synthetic package can launch after fresh metadata verifies, with identical package hash and registry version pointers. Do not install an update to demonstrate recovery. If current metadata revokes/withdraws that package or its grant, keep it blocked and escalate; renewal must not undo the restriction.
4. Retain a redacted record of source SHA, private profile/environment, operator/reviewer, old/new sequences and expiry, signature-verification result, metadata object hashes/ETag outcomes, package hash/byte-count comparisons, registry-pointer comparison, blocked-expired behavior, and successful post-renewal behavior. Include failure/partial-publication recovery if it occurs. Never retain private keys, credentials, patient information or raw profile contents.

### Drill limits

The drill proves continued **staging app-feed** operation and expired-feed recovery only. It does not establish production key custody, platform updater behavior, customer host support, production availability, or G20/G21 acceptance. This P08 worker performs no staging or production mutations; all steps above await M15.5 execution by the assigned operator under the reviewed staging procedure.

## Bounded support and recovery procedure

1. Ask the user to use the existing explicit safe-diagnostics preview/export only when useful. The existing event store is fixed-schema and bounded to a 256-entry ring and 32 KiB file; it contains versions, platform/architecture and approved event codes, not account/clinic IDs, operation IDs, URLs, paths, credentials, patient data, drafts, screenshots or arbitrary exception text. Export is local and user-directed; there is no telemetry/upload step.
2. Identify the platform/app version, host/architecture, app ID/release digest, current catalogue and policy sequence/expiry, and visible error code. Do not collect bearer tokens, signing material, raw clinic requests or patient payloads. Preserve the user's live profile and app session while collecting diagnostics.
3. For expired/unavailable metadata, explain that a fresh signed control feed is required. Leave installed packages, active/known-good pointers and anti-replay watermarks intact; do not clear caches, reset registry state, force a launch, downgrade, or delete package files. Escalate to the assigned staging operator for a reviewed higher-sequence metadata renewal. If controls remain expired, preserve fail-closed behavior and keep the current installation available for later safe recovery.
4. For corrupt/lost watermark, registry or journal state, stop unsafe operations and follow the existing recovery-only path in [SECURITY_AND_RECOVERY.md](../../../docs/SECURITY_AND_RECOVERY.md). Preserve suspect bytes and transaction evidence for engineering review; never silently reset the watermark or perform generic profile rollback. If trusted-key compromise is suspected, halt publication and use the separately reviewed trust-root/platform-release process; remote metadata signed by a compromised key cannot securely revoke itself.
5. Record only the redacted event, exact source/build and environment, observed sequence/expiry, action and result. Any support escalation involving platform installer/updater incidents, host permissions, compatibility retirement or production release belongs to M20's G20 runbooks.
