# P04 — First-Party App API Authority and Compatibility Proposal

**Status:** Lead decisions recorded 2026-10-22: existing pinned company trust roots and fresh signed company catalogue/update-policy metadata are the API approval authority; format 1 is insufficient for release-scoped grants, so format 2 is required. Runtime/document-contract work remains pending.

**Scope:** M15.2 API-permission evolution only. This file does not implement runtime behavior, amend the global checklist, or resolve M14 media/navigation work.

## Decision to make

Define how a signed first-party app release receives only its approved API operations while the desktop binary stays unchanged across both app scenarios. “Unchanged desktop” means the fixed desktop source/binary after the M15 host API contract and its supported operations have been accepted. It does not mean the earlier M15.1 checkpoint already contains every M15 host contract needed by M14. P04 must prove both a newly signed app and an API-only extension of an existing app on that same accepted host baseline. The M14 register's P01 remains a prerequisite for the final per-app route, method, payload, and role inventory.

The accepted SDK/API contract says app code expresses named intent through the platform broker. The broker owns caller binding, validation, session checks, credentials, and transport; the existing Dental SaaS Worker remains the authority for business rules, clinic access, and transactions. R13 continues to prohibit general app-to-app messaging, direct app invocation, and arbitrary intents.

## Current evidence and constraint

- Package signatures bind company publisher, app ID, version, and package digest. Package capability declarations describe what the app asks to use; package contents and package signatures alone do not grant API authority.
- The signed company catalogue already identifies a release by app ID, version, package hash, and payload digest and carries a capability list. The signed update policy carries an app-level capability ceiling, minimum version, expiry/sequence, and revocation controls. Both are checked against company trust roots pinned by the desktop. This is the accepted approval authority; no new API-specific trust root or key-purpose pin is proposed.
- The broker binds a registered frame, origin, app ID, version, and session generation. It holds credentials and transport in the host. It checks the signed package capabilities and current session authority at request time.
- Clinic API path authority is still coupled to app IDs in compiled `electron/sdk/appPolicy.ts`. Most app entries use path prefixes; Follow-ups has narrower path/method/query checks. Generic `clinic.api.request` accepts a renderer path and method which are then filtered by that host policy. Signing a new package does not independently add a new app ID to that route policy.
- SDK 1.1 / API major 1 already contains typed appointment operations, generic clinic request/read operations, and local platform operations. The accepted M15 host baseline must define the complete closed operation contracts required for the proof. App-only releases can receive metadata approval only for operations that baseline already understands.
- Existing limits remain: 12,000-character JSON body, 16 KiB request envelope, 256 KiB JSON response, and 8 MiB blob read. M14 P02/P09 identify upload needs beyond the current blob-read contract. P04 does not change those limits or approve binary upload.

See the [SDK/API broker contract](../../../dental-os_v1-documentation/11_V1_SDK_AND_API_BROKER.md), [API/update audit](../../audit-reports/API_UPDATE_GAPS.md), and M14's [pinned dependency register](https://github.com/Business-It-Partners/dental-os/blob/codex/milestone-14/dental-os_v1_working_info/milestone-14-dental-app-functionality/PLATFORM_DEPENDENCIES.md) at `48c18401cada192bfa0bea02a4afdd0cb10e45ca`.

## Accepted authority and grant semantics

Use Option C. The accepted trust chain is the existing desktop-pinned company trust roots plus fresh signed company catalogue and update-policy metadata. No separate API-grant signing key or key-purpose pin is introduced. Existing authorized company metadata publication controls remain the path for issuing and revoking approvals.

Format 1 is insufficient for release-scoped API authority. Its catalogue permits only one entry per app, while its update policy stores capabilities per app rather than per package digest. A successor could therefore widen the current app-level set and accidentally widen an older retained package that already declares a broad SDK operation; the same format cannot independently preserve a narrower grant for an eligible known-good fallback.

The exact API grant must be carried in a **format-2 signed update policy** as a grant record for each immutable release identity: company app ID, version, package wire hash, payload digest, and exact host-defined API operation IDs. The policy's existing app-level SDK capability set remains a maximum ceiling, with minimum-version and revocation controls. For the current catalogue release, the catalogue identity must match the format-2 release record; its existing capability list continues to describe the package's SDK declarations and is checked against the verified package and app-level ceiling. That list is not the API grant and cannot substitute for a missing policy grant. Older locally retained versions need not appear as catalogue releases, but they must retain their own valid format-2 grants to remain launch/fallback eligible.

The update-policy grant list must retain an entry for every distinct eligible active, pending, trial, or known-good release. Bound entries to the package registry's current maximum of three retained release versions per app; if lifecycle state ever requires more, revise the registry/policy limits together instead of truncating a needed grant. Include a candidate release when it can be installed/staged; it counts against the same retained-version budget when staged. Remove an entry only when that exact release is no longer retained/eligible or is explicitly revoked. If no safe slot remains, defer staging instead of dropping a grant for an eligible fallback. The signed package manifest remains a declaration of SDK entry points, not API authority. A broad entry point such as `clinic.api.request` cannot stand in for exact API operations: the host resolves each request to a closed operation ID and checks that ID against the matching format-2 release grant. For an installed fallback, current format-2 minimum-version, digest-revocation, and compatibility controls determine continued eligibility; the older release need not remain the single catalogue row. Both signed metadata documents must be authentic, fresh, sequence-valid, environment/channel-consistent, and mutually consistent.

The effective API set is the intersection of (a) the exact format-2 update-policy grant for the verified app ID/version/digests, (b) closed operations implemented by the accepted M15 host contract, and (c) operations allowed by the current Worker-derived clinic session. Each host operation also identifies its required SDK broker entry point; both the verified package declaration and the policy's app-level SDK capability ceiling must allow that entry point. A broad entry point grants no route or business operation by itself. For the current catalogue release, require its package identity to match the format-2 record and enforce existing package/catalogue SDK-capability compatibility. Fail closed on disagreement. Never silently broaden or reinterpret a grant. The Store/registry/broker must carry and enforce the exact release identity, not just an app ID or display name.

The host should authorize a call only when all of these are true:

1. The package's company publisher, stable app ID, signature, and immutable content digest verify under first-party trust. There is no third-party publisher or sideload path.
2. Fresh catalogue and **format-2 update-policy** metadata verify under company roots already pinned by the desktop, match environment/channel and current anti-replay watermarks, and name a mutually consistent company release. A format-1 app-level policy is insufficient to authorize clinic API calls.
3. Each API operation ID resolves to a closed contract in the accepted M15 host code: fixed Worker route/method or typed handler, input/response schema, allowed query/body fields, role/session prerequisites, idempotency behavior where applicable, and current limits. The format-2 policy carries operation identifiers only; it cannot supply endpoints, schemas, roles, tenants, or code. A generic SDK transport capability is not sufficient authority. Renderer-supplied URLs, methods, headers, tenant IDs, roles, or credentials never define authority.
4. At launch, the exact active package version and digests match an eligible format-2 grant record and the package is compatible with the accepted desktop SDK/API contract. A new/current candidate also must be approved in the fresh catalogue; an installed fallback must satisfy current minimum-version, digest-revocation, and rollback policy. An absent, stale, replayed, malformed, incompatible, or unverifiable grant fails closed.
5. On every broker dispatch, the host re-matches the host-bound package version/digests against current format-2 policy and enforces only that release's operations plus current session generation. The Worker independently authorizes the actual business operation and tenant. A host grant never overrides a Worker denial.

For the two required proofs, use operations already implemented by the accepted M15 desktop contract, such as `appointments.list` and then `appointments.setStatus`, with a synthetic Worker transport. The M15 host-contract work may add or refine operation definitions before the proof baseline is frozen. Once frozen, a new Worker route or operation contract absent from that host catalog requires a later desktop/API-contract release; it must not be smuggled in as an arbitrary path, message, intent, or broad `clinic.api.request` grant.

Keep the accepted SDK/API major compatible for an app-only extension that uses existing host-defined operation contracts. A compatible minor addition may expose an existing host operation to a particular approved release; it does not alter that operation's request/response meaning. If establishing the M15 host contract adds operation identifiers or SDK-visible semantics, version that host contract appropriately before freezing the proof baseline. Breaking schema, route, security, or business-semantic changes require an explicit API-major or platform contract decision and an incompatible release must be refused. The old package digest retains only its old authority; a successor's added approval must not retroactively widen an older or rolled-back package.

Retain existing 24-hour metadata freshness and monotonic sequence/replay protections. Format 2 is a schema evolution of the existing signed update-policy authority, using its current pinned company roots and signing purpose; it adds digest/version-scoped release grant records while preserving the app-level SDK capability ceiling and lifecycle controls. No new signing key, trust pin, API endpoint, or metadata-defined route is introduced. The catalogue's single current-release identity must match its format-2 grant, while format 2 retains any additional eligible local fallback/trial release grants.

## Compatibility and version behavior

- **Compatible additive release:** app remains compatible with the SDK/API contract frozen in the accepted M15 desktop, uses an operation already present in its host catalog, and keeps all pre-existing operation contracts stable. App version/package digest and signed release metadata change; only the exact newly approved release receives its added operation. The desktop may have changed while establishing the M15 host contract, but it remains byte/source-identical across both app-only proof scenarios.
- **No silent capability inheritance:** the format-2 update policy keeps distinct grants for distinct immutable releases. A prior release, a different digest, an app with a reused display name, or a rollback package receives only its own retained approved operations.
- **Host or Worker evolution:** a new API operation definition, new authority primitive, changed payload limits, or changed endpoint semantics is not app-only compatibility. It needs a reviewed desktop/API contract change; Worker authorization remains required.
- **Unknown major or removed operation:** do not start the incompatible release and do not silently substitute a similarly named operation. Report an incompatibility through the existing safe Store/runtime error path.
- **Policy format transition:** format 1's app-wide operation set cannot authorize clinic API calls. The accepted M15 desktop must support signed update-policy format 2 before the proof; missing format-2 metadata or an absent exact release record denies API authority and blocks that release from API-enabled launch/fallback.
- **Session changes:** re-evaluate current host/session authority per call. Lock, logout, account/clinic switch, role change, or generation change removes old authority and drops stale results. A write already dispatched may have an unknown server outcome and retains its original idempotency key; local cancellation is not server rollback.
- **Limits and boundaries:** retain the current JSON/envelope/response/blob-read limits pending sanitized synthetic measurement. No media upload, print/export adapter, cross-app navigation permission, or app-to-app message is granted by API approval.

Signed metadata may name an existing operation ID but never define a route, method, schema, or new operation semantics.

## Risks and dependencies

- A compromised or over-broad company metadata signing key could grant excessive first-party access within the platform ceiling. Preserve existing root custody, expiry/sequence, revocation, audit, and recovery controls; this proposal adds no separate API key or pin.
- A broad operation such as generic `clinic.api.request` could defeat least authority if approval names only that SDK capability. Host route/method/schema contracts must be exact; M14 P01 must supply app-specific route/method/payload/role needs before final grants.
- Host operation contracts and Worker behavior can drift independently. Every operation needs a reviewed compatibility owner and negative contract test; app-only grants cannot add backend semantics.
- Existing role and `clinic.app.*` family filtering is compiled and keyed by known app IDs. P04 implementation must define how a new app maps to existing Worker-derived capabilities without trusting package claims or weakening current app-family restrictions.
- M14 P03's stable operation identity/outcome adapter, P02/P09 media upload, P11 measured payload needs, and P10 navigation remain separate dependencies. None is resolved by this authority proposal.
- Format 1 cannot scope an API grant to a retained release. Format 2 must maintain a distinct grant for each eligible digest/version; if a record is missing or mismatched, that exact package is not API-authorized and must not borrow another version's grant.

## Lead decision and integrated implementation — 2026-10-22

The user selected **the existing signed company catalogue/update-policy authority**. This decision reuses the existing company trust roots, signature purpose, environment, freshness, sequence and revocation controls. No new API key/pin, endpoint, route manifest, publisher or app-to-app primitive is added. The accepted record shape is the one above: update-policy format 2, exact `{version, packageSha256, payloadDigest, apiOperations}` records, at most three retained release records, app-level capabilities and company trust as ceilings, and catalogue identity matching for the current candidate. Format 1 continues only its existing update-safety role and returns no typed API grant.
