## Scope

Clinical encounter from case/patient selection through an in-memory draft, review, and the SaaS atomic commit; optional payment/closure only when the session permits it.

M18 exercises the signed app through the Dental OS connected to the real SaaS staging backend; no mock API is used for staging acceptance. Use only designated test data. A uniquely labeled test patient/case created through normal staging app screens is a real staging record, not a mock. Production is out of scope. No backend code or direct backend data changes are allowed as an app fix. Route calls listed here are expected through the signed app's SDK and host broker; they are not authorization to call those endpoints directly.

## Prerequisites and staging environment

- Confirm a staging-only Dental OS session and verified staging Store/Worker environment; record the app ID, installed version/digest, feed sequence and desktop commit.
- Install/open the exact signed staging package through the Dental OS Store/window lifecycle; do not infer the installed version from a local directory.
- Confirm actual staging clinic, role and capabilities from the session; do not assume the login's role. Read-only checks may use an existing case explicitly labeled for staging testing. For writes, use a dedicated test patient/case created through the staging UI or explicitly designated by the user; never write to an unverified patient's chart.
- Ensure read-only staging request tracing or request/correlation IDs are available to verify calls and responses without exposing tokens or PII.
- Verify the current app route, permission and payload contract against the M17 plan and package adapter before writes. Stop and record BLOCKED if the expected role, seed, trace or safe failure fixture is unavailable.
- Parent-plan execution controls, issue taxonomy and backend handoff rules apply.

## API reachability and expected calls

Expected reads are GET /v1/work-entry/cases plus patient lookup/core, staff references, treatment protocols, case work-entry, odontogram/periodontal/canal data, permitted follow-ups, lab suppliers/orders and patient ledger. The principal write is POST /v1/work-entry/commit with expectedCaseRowVersion and the full supported draft. Separate explicit case commands exist only where the pinned SaaS contract specifies them. All requests use ClinicClient; the Worker is the authority for the atomic transaction.

Record each observed call, response status/shape and request ID in the shared [test template](TEST_CASE_TEMPLATE.md). Include missing, unexpected, duplicated or direct-network calls as findings. Startup reads must not be confused with completed business workflow acceptance.

## End-to-end workflows and important states

Select a designated staging test patient/open case; load existing clinical plan/chart; enter chief complaint/notes, plan stages and completion, clinical charts, prescription, lab order, follow-up, optional payment and close disposition; review and submit once; reopen the case and ledger to confirm the canonical atomic result; exercise validation, dirty protection, role denial, stale case revision and lost response. Test-data writes must be made through the actual Dental OS UI and staging API.

The current signed Work Entry 1.0.3 package opened from the staging Store. Startup GETs for `/v1/work-entry/cases`, `/v1/treatment-protocols`, and `/v1/clinic/staff-references` each returned HTTP 200. ## Issue classification

Use the shared categories in the [main M18 plan](PLAN.md#issue-classification). App-specific ownership hints:

- **OS/platform fixture:** an otherwise correct package/session is blocked by the shared host, signed Store lifecycle, SDK broker, route allowlist, capability gate, window or media broker.
- **App implementation:** this app issues the wrong query/body, renders the wrong state, loses its draft, duplicates a write or fails to refresh from the Worker.
- **Backend:** a correct authorized app request reaches staging but the Worker/SaaS violates the reviewed route, role, tenant, persistence, validation, idempotency, audit or response contract.
- **Test/environment:** wrong target/package/seed/role, staging outage, missing test fixture or trace, or no safe way to trigger a recovery condition.

Determine the failing boundary before assigning ownership. If evidence is insufficient, classify UNKNOWN and gather a redacted trace rather than guessing.

## Reporting backend-owned issues

For a backend-owned issue, copy the [backend handoff fields](TEST_CASE_TEMPLATE.md#backend-owned-issue-handoff) into a sanitized report: app/package/version/digest, M15 commit and staging sequence; synthetic fixture namespace and pseudonymous IDs; role/capabilities; numbered UI reproduction; expected versus actual; method/path/query; status and redacted response; request/correlation ID; idempotency and row-version observations; post-refresh state; evidence references. Remove credentials, tokens, cookies, patient/staff PII, signed URLs and raw files. Identify the owner as the user's backend team. The M18 worker records the issue for lead review and does not modify backend code or data.

## Acceptance criteria

The read paths, final atomic commit boundary, data scoping, optional capability gates, validation, stale-revision behavior and same-key unknown-outcome recovery are demonstrated with synthetic staging data. No renderer-side write fan-out or backend implementation change is introduced.

A case is PASS only when its real staging app workflow and API behavior were exercised and evidence is attached. An unavailable role/account, unavailable failure fixture or unexecuted workflow remains BLOCKED or NOT RUN. App acceptance is tied to the exact signed staging package digest and desktop commit; the primary FLOW-03 path passes for 1.0.5, while overall M18.4 remains IN PROGRESS because the other listed scenarios are unrun. Later package updates require retesting affected cases.
