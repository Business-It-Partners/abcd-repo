## Testing boundary

- M18 targets the Dental SaaS staging Worker through the connected Dental OS and its approved SDK/broker.
- Production calls are prohibited unless the user separately requests production testing.
- Synthetic-only staging data is required. App workflows may create test records through normal app screens; testers must not write directly to backend storage or change shared clinic records.
- An app/OS code fix must not modify Dental SaaS backend code or backend data. Backend contract, authorization, persistence, tenant-scope and response issues go to the user's backend team with redacted reproduction evidence.
- API expectations are derived from the app's existing M17 plan, package API adapter/manifest, and current SaaS contract. Freeze the route/method/payload before execution; do not invent a route to make a test pass.
- A role or tenant check only passes when the actual signed-in staging role/tenant and the request boundary are recorded. A single account does not establish all role coverage.

## Issue ownership and evidence

Each failure is assigned a primary category: OS/platform fixture, app implementation, backend, or test/environment. Ambiguous ownership stays UNKNOWN until the package version, environment, session/capability state, SDK dispatch and Worker response can be distinguished.

Backend issue reports use the shared template and include sanitized reproduction steps, route/method/query, redacted request/response, status, request ID, synthetic fixture namespace, post-refresh state, and idempotency/row-version observations. Never include passwords, ID/access/refresh tokens, cookies, patient or staff PII, signed URLs, raw private files, or replayable secrets. The issue record remains a handoff item for the user; M18 does not send it to a backend channel automatically.
