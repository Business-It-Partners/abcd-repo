### Request scope review

The app cannot currently restrict its request to a synthetic patient ID or namespace. On initialization it checks the app capability and automatically calls `refresh()`, which issues `GET /v1/treatment-progress` with no query parameters. `ClinicClient.read` sends that path as a GET with no request body. Patient search and doctor filtering run locally against the returned rows, after the clinic-wide response has already arrived. The imported API contract describes the response as a clinic-wide incomplete-treatment worklist.

Therefore, confirming fixture IDs alone is not sufficient to make this route safe to open: the request would still fetch the clinic-wide projection. Before any live route call, the lead must confirm the entire eligible projection for this staging clinic is synthetic-only, or provide a backend-supported server-side fixture scope and a corresponding app release. No API call has been made to test either condition.

The source-defined first-party workflow for creating a safe positive fixture is:

1. In **Patient Record**, register a synthetic patient using the normal intake flow if a synthetic patient does not already exist.
2. In **Work Entry**, choose **New case** for that registered synthetic patient and save a distinct chief complaint. The app creates the case open.
3. Open the case, choose an active template under **Add treatment protocol**, provide its required tooth or treatment-area value, then add the protocol.

The minimum state for a Treatment Progress row is an active patient, an open case, and a non-cancelled plan with at least one pending stage. A single pending stage is enough for a positive row; completion, a doctor attribution, a balance, and a return date are not required to render it. Avoid recording completed work for the minimal fixture because that workflow has clinical and financial effects.
