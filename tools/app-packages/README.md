# Internal app-package tooling

The normative wire contract is [dentalpkg/1](../../dental-os_v1-documentation/23_V1_PACKAGE_FORMAT.md). Trusted code is currently `electron/packages/`; compile with the existing controlled build before running tools. No dependency install is needed.

`node tools/app-packages/build.mjs <manifest.json> <assets-dir> <key-id> <external-private-key-path> <new-output.dentalpkg>` assembles in sorted order and refuses existing output. Input manifest has exactly appId, publisher, version, entry, sdkMajor, apiMajor, capabilities (no format/assets fields). It must match a separately approved platform trust policy; building alone cannot authorize execution. Keep release private keys in protected release infrastructure; never put them in this checkout, packages, artifacts or chat.

`node tools/app-packages/generate-fixtures.mjs --test-only` deliberately regenerates the two synthetic packages and their public key using a fresh ephemeral signing key, then discards that private key. Outputs must be reviewed and committed together. Do not regenerate during normal checks; existing signed fixtures are stable across launches and hosts. The normal platform policy trusts neither this key nor these sample IDs. No release private key is supplied or generated for production by M06.

M06 has no renderer install path, file picker, package discovery or production sideload command. These assembly commands produce files only. M07 adds approved distribution; M08 adds full update/revocation/rollback policy.

`node tools/app-packages/prepare-onboarding-release.mjs --staging-only <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json> <version>` prepares one capability-free `company.sample.preview` successor for the synthetic onboarding fixture. It verifies the prior pinned staging signatures, preserves existing app entries and update controls, and requires output/key paths outside the checkout. Fixture versions 1.0.0–1.3.0 remain local under `fixtures/runtime-apps/onboarding/`. It never uploads. The public staging rows for `company.sample.alpha`, `company.sample.beta`, and `company.sample.preview`, and their 18 R2 package objects, were removed at sequence 79; the older live onboarding publication/acceptance instructions below are historical and must not be used to republish these samples to staging.

The authenticated service acceptance is `node tools/verify-staging-onboarding-auth.mjs --staging-auth-readonly` after the controlled build. The full private-desktop staging acceptance is `npm run test:staging-onboarding-desktop`. Both require `DENTAL_OS_STAGING_ACCEPTANCE=true` and `DENTAL_OS_STAGING_CREDENTIAL_FILE` pointing to an external mode-600 JSON file with exactly `email` and `password`; never place credentials in the checkout or artifacts. The service verifier checks staging Firebase/Worker and public R2 reads. The private UI test uses the isolated display runner and verifies live Store first install, arrival flight, app update, and process restart. Both keep credentials in memory and write redacted results under `artifacts/`. The separate private UI fixture acceptance is `npm run test:onboarding`. These checks use only the synthetic company preview app and do not read or modify clinic/business records.

`node tools/app-packages/prepare-m13-batch-release.mjs --staging-only <m13-5-7|m13-8-10|m13-11> <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares one exact M13 first-party app-shell batch for Cloudflare staging. It validates app IDs, 1.0.0 package manifests and module-label inventories, preserves all previously signed catalogue and policy entries, and never uploads. Keep the signing key, prior metadata and generated output outside this checkout. Publish only through the named temporary staging-publisher flow; never production.

`node tools/app-packages/prepare-m13-multimodule-update.mjs --staging-only <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares the Finance and Lab Tracker shared-window-contract patch. It replaces only those two catalogue releases with version 1.0.1, preserves their access policies and all other signed release entries, and never uploads. Keep signing material, prior metadata and generated output outside this checkout; publication remains a separate staging-only step.

`node tools/app-packages/prepare-m17-treatment-protocols-release.mjs --staging-only <external-m17-key> <next-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares the new `company.dental.m17.treatment-protocols` 1.0.0 release. It requires the pinned M17 suite signer and fresh M17-signed feed baselines, appends one package identity and its exact API grant, and writes outside this checkout. Validate and publish only with `publish-m17-treatment-protocols-staging.mjs`; it uploads to the named staging bucket via a temporary nonce-protected Worker and preserves all existing release rows. Never target production.

`node tools/app-packages/prepare-m17-app-release.mjs --staging-only <external-m17-key> <higher-sequence> <m17-app-id> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json> [--grant-work-entry-media]` prepares an immutable M17 release from its retained manifest and built assets. Supported IDs are `company.dental.followups.m17`, `company.dental.appointments.m17`, `company.dental.calendar.m17`, `company.dental.treatment-progress.m17`, `company.dental.work-entry.m17`, `company.dental.patient-record.m17`, `company.dental.m17.treatment-protocols`, `company.dental.finance.m17`, `company.dental.lab-tracker.m17`, `company.dental.staff.m17`, and `company.dental.user-management.m17`. It validates the selected app family and exact ordered module inventory, enforces the shared 64-app ceiling, and writes outside this checkout. The opt-in `--grant-work-entry-media` mode applies only to an existing Work Entry app update and permits exactly the `clinic.media.read` and `clinic.media.upload` additions, with no capability removals; it updates the app-level policy ceiling while keeping each package's API operations exact to its signed release grant. All other app capability changes remain rejected. The signed update policy retains at most seven exact API release grants per app; when a new release exceeds that ceiling, the oldest grant is retired unless rollback metadata depends on it, and the minimum supported version advances to the oldest retained grant when needed. Older package objects remain immutable in storage, but a retired grant no longer authorizes that package's API access. Publish only with `publish-m17-app-staging.mjs`; verify public package bytes, signature, and exact update-policy grant with `verify-m17-staging-packages.mjs`. These releases are staging-only and do not close live clinic acceptance or production gates.

The M17 staging publisher refuses `--apply-staging-only` when the prepared directory already contains `publication-result.json`. After an ambiguous publisher result, read back and verify the signed public catalogue, update policy, exact package bytes/signature, and isolated registry behavior; prepare a fresh directory against the current feed before any retry.
