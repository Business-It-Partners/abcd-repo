# Internal app-package tooling

The normative wire contract is [dentalpkg/1](../../dental-os_v1-documentation/23_V1_PACKAGE_FORMAT.md). Trusted code is currently `electron/packages/`; compile with the existing controlled build before running tools. No dependency install is needed.

`node tools/app-packages/build.mjs <manifest.json> <assets-dir> <key-id> <external-private-key-path> <new-output.dentalpkg>` assembles in sorted order and refuses existing output. Input manifest has exactly appId, publisher, version, entry, sdkMajor, apiMajor, capabilities (no format/assets fields). It must match a separately approved platform trust policy; building alone cannot authorize execution. Keep release private keys in protected release infrastructure; never put them in this checkout, packages, artifacts or chat.

`node tools/app-packages/generate-fixtures.mjs --test-only` deliberately regenerates the two synthetic packages and their public key using a fresh ephemeral signing key, then discards that private key. Outputs must be reviewed and committed together. Do not regenerate during normal checks; existing signed fixtures are stable across launches and hosts. The normal platform policy trusts neither this key nor these sample IDs. No release private key is supplied or generated for production by M06.

M06 has no renderer install path, file picker, package discovery or production sideload command. These assembly commands produce files only. M07 adds approved distribution; M08 adds full update/revocation/rollback policy.

`node tools/app-packages/prepare-onboarding-release.mjs --staging-only <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json> <version>` prepares one capability-free `company.sample.preview` successor for the approved synthetic onboarding test. It verifies the prior pinned staging signatures, preserves existing app entries and update controls, and requires output/key paths outside the checkout. Fixture versions 1.0.0–1.3.0 are under `fixtures/runtime-apps/onboarding/`. It never uploads. Use only with the existing named Cloudflare staging operator flow; never production.

The authenticated service acceptance is `node tools/verify-staging-onboarding-auth.mjs --staging-auth-readonly` after the controlled build. The full private-desktop staging acceptance is `npm run test:staging-onboarding-desktop`. Both require `DENTAL_OS_STAGING_ACCEPTANCE=true` and `DENTAL_OS_STAGING_CREDENTIAL_FILE` pointing to an external mode-600 JSON file with exactly `email` and `password`; never place credentials in the checkout or artifacts. The service verifier checks staging Firebase/Worker and public R2 reads. The private UI test uses the isolated display runner and verifies live Store first install, arrival flight, app update, and process restart. Both keep credentials in memory and write redacted results under `artifacts/`. The separate private UI fixture acceptance is `npm run test:onboarding`. These checks use only the synthetic company preview app and do not read or modify clinic/business records.

`node tools/app-packages/prepare-m13-batch-release.mjs --staging-only <m13-5-7|m13-8-10|m13-11> <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares one exact M13 first-party app-shell batch for Cloudflare staging. It validates app IDs, 1.0.0 package manifests and module-label inventories, preserves all previously signed catalogue and policy entries, and never uploads. Keep the signing key, prior metadata and generated output outside this checkout. Publish only through the named temporary staging-publisher flow; never production.

`node tools/app-packages/prepare-m13-multimodule-update.mjs --staging-only <external-m08-key> <increasing-sequence> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares the Finance and Lab Tracker shared-window-contract patch. It replaces only those two catalogue releases with version 1.0.1, preserves their access policies and all other signed release entries, and never uploads. Keep signing material, prior metadata and generated output outside this checkout; publication remains a separate staging-only step.

`node tools/app-packages/prepare-m17-app-release.mjs --staging-only <external-m17-private-key> <strictly-higher-sequence> <m17-app-id> <new-output-dir> <prior-catalogue.json> <prior-update-policy.json>` prepares a local M17 Follow-ups, Appointments, or Calendar release using the package's manifest version. A new ID must start at 1.0.0; an existing ID must advance beyond its signed current version. Updates preserve the current catalogue identity, all older package grants, and unrelated metadata entries. It verifies each prior signed envelope using the key ID recorded in that envelope, requires matching prior sequence/timestamps and a strictly higher new sequence, and signs new package/metadata only with the pinned M17 key. The key, input metadata and new output directory must be outside this checkout; output must be new. It does not upload, publish, activate, install or deploy anything.

`node tools/app-packages/publish-m17-app-staging.mjs --validate-staging-only <prepared-release-dir> <existing-wrangler-runtime-root>` validates a prepared Follow-ups, Appointments, or Calendar first release/update against the exact staging feed baseline without publishing. The explicit `--apply-staging-only` mode writes the immutable package object and advances signed metadata using a temporary nonce-protected Worker and conditional writes to the pinned Cloudflare staging bucket; it never targets production. Updates must keep prior package grants and all unrelated app entries unchanged. The prepared release and Wrangler runtime must remain outside the checkout. The Worker is removed after the operation, and replay/anonymous access checks must pass. Re-read the public feed after publication.

`node tools/verify-m17-staging-packages.mjs` performs read-only public catalogue, update-policy, signature, package hash and grant checks, then smoke-installs and removes the current Follow-ups, Appointments, and Calendar M17 packages in an isolated local registry. It also checks that the Appointments 1.0.0 policy grant remains alongside its current update grant. This does not authenticate to the clinic API and is not an authenticated Store acceptance.

`node tools/verify-staging-m17-app-install.mjs` runs the authenticated staging Store-service install check for both published M17 packages. It requires `DENTAL_OS_STAGING_ACCEPTANCE=true` and `DENTAL_OS_STAGING_CREDENTIAL_FILE` pointing to an external mode-600 JSON file with exactly `email` and `password`. It creates a disposable local package profile, verifies install policy, signed package identity/bytes and package-bound API grants, and removes the profile. It does not run app renderer workflows or clinic business API operations and does not produce a runtime health receipt. Keep credentials out of chat, checkout, and artifacts.

For private Linux Store-to-renderer acceptance, run `node tools/run-ui-test.mjs tests/m17-staging-live-desktop.mjs` with those same opt-in environment variables and credential-file requirements. This opens each exact current published package in the Dental OS-managed renderer, verifies the automatic payload-bound health receipt, and removes the private profile. Initial app startup reads staging data through the broker; this check performs no business writes and does not cover role/tenant feature workflows or physical Windows.
