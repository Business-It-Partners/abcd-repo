`clinic.media.upload` is an explicit signed format-2 exact-release operation. Patient Record may upload patient media and Staff may upload Staff documents, subject to package, app-family and trusted session access. Worker authorization and tenant selection remain authoritative. Read permission does not imply upload permission; Work Entry's read scope is unchanged.

The standard host session gate permits the `clinic.app.patient-record` family to upload `patient_media` under `patient_record.access`, or the `clinic.app.staff` family to upload `staff_document` under `staff.manage`. Any approved company ID can select one of those existing families through its signed package capability; no per-ID upload rule is compiled. The host denies uploads before sign-in, while locked, after sign-out, for mismatched family/kind pairs, and for unsupported families. The broker checks the exact signed operation grant as well; credentials stay in the host and the Worker derives clinic tenancy from the authenticated token. No public package grant is included in this local source change.

## Wire protocol

1. `begin`: `{action:'begin', kind, recordId, metadata, idempotencyKey}` allocates one explicit transient buffer. Patient media may additionally specify `replacement:{assetId,reason}` to select only the existing fixed replacement-intent route; Staff replacement is refused. The Worker preserves the original clinical file until successful replacement finalisation. Metadata has the exact domain fields validated by `mediaUploadContract.ts`; no caller checksum, URL, headers, tenant or storage key is accepted. It returns `{transferId, received, total}`.
2. `chunk`: `{action:'chunk', transferId, offset, data}` supplies canonical base64 for at most 8 KiB. Each request fits the unchanged 16 KiB SDK envelope. App/frame ownership is bound by the broker. Chunks are sequential; identical replay of received bytes is safe and changed/overlapping bytes are refused. Once remote intent processing starts, bytes cannot change.
3. `commit`: `{action:'commit', transferId, idempotencyKey}` must use the original key. The host computes SHA-256, creates the intent, verifies the returned ID/parent/MIME/size/checksum and exact fixed upload path/header, PUTs bytes to its own fixed Worker URL, and finalises. Distinct stable per-stage keys derive from the original key. Only the confirmed `{committed:true, assetId}` result reaches the app; private handles and credentials remain in main.
4. `cancel`: the same identifiers/key discard unsent bytes or explicitly abort a known/unknown pending intent. An unknown intent response is resolved with the original key first. If finalisation already committed, return `{cancelled:false, committed:true, assetId}` after authoritative metadata verification. Never imply that cancelling undoes a clinical fact.

A lost remote response returns `UNKNOWN_OUTCOME`; the transfer remains available for explicit same-key commit/cancel. A PUT/finalise conflict can be reconciled only against an active object with the same ID, parent, MIME, byte count and checksum. Changed bodies cannot reuse the key. Bounded transient terminal receipts let the app retrieve a confirmed result after a lost SDK reply without retransmitting bytes. These receipts are observations of server responses, not a local business database.

## Bounds, lifecycle and remaining verification

Patient media remains at most 10 MiB; Staff documents at most 25 MiB. There is one transfer per registration and two broker-wide, with 128 terminal receipts, a five-minute memory lifetime and a 60-second commit/cancel deadline. Begin/chunk perform no remote writes. Buffered and unknown work participates in the shell close/update safety gate. Successful completion, cancellation, frame removal, logout and session invalidation clear/zero the buffer; no file or offline retry queue is created. Expiration performs no background network work and does not claim to undo remote state. In-flight expiry is cleaned up when the bounded request finishes.

Backend `307a21b` exposes authenticated owner-scoped expired/cleanup-pending discovery and abort actions. The staging recovery check reconstructs the broker/session and reselects the same source file; it does not persist transfer bytes, create an offline queue, or test OS-profile persistence. Exact-size staging uploads, one-byte-over host rejection, fresh-session recovery after a dropped content response, Staff finalise-response reconciliation, and full-size readback integrity are verified. Record reads and both upload-intent paths were denied across two real staging clinics. The earlier media-read probe used withdrawn files; a later separate active-file test confirmed both signed Clinic B apps received metadata HTTP 404 and broker `ACCESS_DENIED`, with no binary request or bytes returned. Synthetic patient and Staff media records were withdrawn after acceptance; the Worker handler changes status and makes no R2 delete call. This run did not check a separate bucket lifecycle or verify object bytes after withdrawal. A later real staging Worker/D1/R2 receipt race returned one HTTP 200 and one HTTP 409 for simultaneous same-key finalise requests; a same-key replay returned the original HTTP 200 receipt. Stored-file status and retention are controlled by Dental SaaS APIs and are not part of the OS media capability. No signed feed grant is published automatically, and no production action follows from this document. The concurrent receipt result was checked against the actual staging Worker; this does not establish a separate bucket lifecycle or eventual cleanup.

Patient X-ray metadata requires a real `capturedOn` calendar date (`YYYY-MM-DD`), matching the existing clinical schema. The host rejects null or impossible dates before any request. Staff `expiresOn` remains nullable.
