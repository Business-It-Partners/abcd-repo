## Current state

**Overall status: B0 COMPLETE — B1 COMPLETE — B2 COMPLETE — B3 COMPLETE — B4 ACTIVE.** V1 targets Brave only; support for other browsers is deferred until all V1 milestones are complete. B2 follows the desktop identity flow in the browser: a five-second minimum brand splash while Firebase restores the saved session, then the clinic sign-in screen or workspace. Valid staging sign-in and saved-session restoration were verified in an isolated browser. A browser-side workspace switch calls the existing Worker role endpoint, closes open app windows, and refreshes `/v1/me` before updating access. Staging sign-in, saved-session restore, token refresh, sign-out, invalid credentials, Admin/Doctor role switching, PIN enforcement, and failure-state recovery were verified in an isolated Brave browser.

The browser edition has a browser-owned desktop shell with the Dental OS wallpaper, static first-party app dock, URL-hash routes, movable/minimizable/resizable windows, and an optional user-triggered full-screen view. The home screen includes the desktop-style status bar, clinic profile, and calendar/time widgets; development and app-update panels remain excluded. Battery status is shown only if Brave exposes a live reading. Visual acceptance of these widgets remains pending. `npm run dev:browser` is an offline preview at `http://127.0.0.1:4280`; it blocks external network connections but allows same-origin requests for package integrity checks. `npm run dev:staging` starts connected mode at `http://localhost:3003` and loads Firebase Auth with the existing staging Web SDK config. It calls the staging Worker's `/v1/me` route and calls `/v1/clinic/workspace-role` only when a user explicitly confirms a role switch. The ten first-party catalog entries are role-filtered and launch inside scripts-only opaque-origin frames through a nonce-bound `MessageChannel`. B4 has added the Treatment Protocols browser UI, host-mediated API bridge, app bundle, capability, and three exact route grants; the other nine apps remain previews without API grants. B4 live workflow acceptance and any business writes are still pending a confirmed synthetic staging target.

The local shell is not an authenticated clinic workflow or app-runtime acceptance. The offline preview at `http://127.0.0.1:4280` intentionally makes no API calls and is not a staging CORS origin. The connected staging mode uses `http://localhost:3003`, which the existing Worker CORS policy allows. B1 and B2 made no SaaS source, Firebase configuration, Worker, or deployment changes.

Read-only staging review is recorded in [Architecture baseline](ARCHITECTURE.md). Firebase CLI confirmed that existing staging Hosting sites have live releases; none was overwritten. The local SaaS checkout had unrelated uncommitted changes, which were left untouched.

## Verification record

Firebase Hosting site listing and release-channel inspection were read-only. B1 used isolated headless Brave 148.1.90.121 to inspect the shell and placeholder-window controls. The B2 browser check loaded the pinned Firebase SDK in isolated Brave, showed sign-in with the dock hidden before authorization, confirmed unauthenticated staging `/v1/me` returns 401 without clinic data, and checked the sign-in layout at 320px. A browser request with an Authorization header also reached the Worker and returned the expected 401, confirming the connected origin's preflight/CORS path. Focused role-filter tests pass for admin, doctor, reception, and missing capabilities. The new desktop-style splash/sign-in layout was inspected in an isolated browser at 780×493 and 320×600, with no horizontal overflow and the sign-in button visible at both sizes. On 2026-10-27, a valid staging login and saved-session restoration were verified in an isolated Playwright browser: Firebase accepted the account, the Worker returned 200 for `/v1/me`, and the session capabilities opened the authorized dock. This exposed and fixed the browser's incorrect assumption that clinic data was at the response top level instead of under `session`. The browser now requests workspace-role changes through the existing Worker endpoint and verifies the new role with `/v1/me`; this does not write clinic business records. Unit tests cover role filtering, role validation, role-switch error mapping, and the confirmation UI. Both extra login-screen buttons (saved-session retry and account sign-out) remain removed; users can re-authenticate through the sign-in form. On 2026-10-27, a forced Firebase ID-token refresh returned 200 from Secure Token and triggered Worker `/v1/me` 200. Sign-out cleared the Firebase session and hid the dock; invalid Firebase credentials displayed the expected error, and valid sign-in succeeded again. Admin→Doctor switching returned 200 and removed Finance from the nine-app Doctor dock. A wrong Admin PIN returned Worker 403 and preserved Doctor access; the valid PIN returned 200 and restored the ten-app Admin dock. Unauthenticated `/v1/me` returned 401 with `clinic_auth_required`. Simulated 403/503 JSON responses and a rejected `/v1/me` fetch hid access; reload recovered through a real staging `/v1/me` 200. The 503/network cases were simulated in the browser; no staging outage was induced. No patient, appointment, billing, or other clinic business records were accessed or changed. The authorized role switch updated the expected role-session/audit state, and the successful PIN check reset the single failed-attempt counter. No SaaS source, Firebase configuration, Worker, Hosting resource, or deployment was changed.

For B3, the catalog and browser-host package hashes are source-controlled together. It rejects unknown metadata and remote paths; app frames receive only `allow-scripts`, have an opaque origin, and communicate over a private channel. On 2026-10-27, isolated headless Brave 148.1.90.121 loaded the `Staff` runtime to `ready`, reported `self.origin` as `null`, denied local storage and parent DOM access with `SecurityError`, and exposed no Firebase config, desktop bridge, or token-like globals. A direct request to a reserved external test domain was blocked by `connect-src 'none'`. The app's ungranted `GET /v1/me` request was rejected by the host and produced no Worker request. A second app frame was also isolated. DevTools intercepted and altered a package response: hash verification failed into the retryable error state, and retry loaded the trusted package successfully. The secure-handshake timeout is source-checked to use the same frame/channel cleanup and retry path, but that specific timeout was not fault-injected in the browser. The runtime CSP pins the exact JavaScript hash. Update behavior keeps a loaded frame's snapshot and adopts a new manifest on host reload; Firebase Hosting rollback is defined as restoring the last known-good host release but remains untested until B6. The focused host/runtime suite passes 15/15, including B4 grant and bundle assertions. No clinic credentials, business data, Worker writes, staging config, or hosting resources were used or changed for B3.

For B4, the Treatment Protocols app UI is connected to the browser runtime, replacing Electron-only SDK/session imports with the host-mediated clinic client and browser history lifecycle. The host grants only `GET /v1/treatment-protocols`, `POST /v1/treatment-protocols`, and UUID-scoped `PUT /v1/treatment-protocols/{uuid}` to the `treatment_protocols.manage` capability. Draft/save lifecycle state guards close, switch-role, and sign-out actions while work is pending. The compiled app includes pinned entry/script/style hashes; its frame CSP still denies direct network access. Local bundle build and TypeScript typecheck pass. Vite reports non-fatal warnings for inherited React `use client` directives in the migrated UI. The local staging origin passed the read-only OPTIONS preflight for `authorization`, `content-type`, and `idempotency-key`. On 2026-10-27, isolated staging verification authenticated an Admin session, launched Treatment Protocols, and received 200 for the granted `GET /v1/treatment-protocols`; the UI displayed 22 rows. No protocol was changed. Some rows are labelled as tests, but the synthetic clinic/record target and cleanup plan are not confirmed. Therefore create/update acceptance, Worker role denial, retry/error handling, saved-state readback, and cleanup remain incomplete; B4 is still active.
