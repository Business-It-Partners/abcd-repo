## Current state

**Overall status: B0 COMPLETE — B1 COMPLETE — B2 COMPLETE — B3 COMPLETE — B4 ACTIVE — B5 IMPLEMENTATION PRESENT, ACCEPTANCE OPEN.** Finance, Calendar, Treatment Progress, Work Entry, and Patient Record implementations are present under B5; browser workflow and visual acceptance remain open while B4's synthetic-data acceptance gate remains open. This does not close or claim B4. V1 targets Brave only; support for other browsers is deferred until all V1 milestones are complete. B2 follows the desktop identity flow in the browser: a five-second minimum brand splash while Firebase restores the saved session, then the clinic sign-in screen or workspace. Valid staging sign-in and saved-session restoration were verified in an isolated browser. A browser-side workspace switch calls the existing Worker role endpoint, closes open app windows, and refreshes `/v1/me` before updating access. Staging sign-in, saved-session restore, token refresh, sign-out, invalid credentials, Admin/Doctor role switching, PIN enforcement, and failure-state recovery were verified in an isolated Brave browser.

The browser edition has a browser-owned desktop shell with the Dental OS wallpaper, static first-party app dock, URL-hash routes, movable/minimizable/resizable windows, and an optional user-triggered full-screen view. App windows now expand with the desktop when browser full screen is entered, restore their normal size on exit, and keep dragged/resized geometry proportional to the available desktop area. The home screen includes the desktop-style status bar, clinic profile, and calendar/time widgets; development and app-update panels remain excluded. Battery status is shown only if Brave exposes a live reading. Visual acceptance of the window behavior and widgets remains pending. `npm run dev:browser` is an offline preview at `http://127.0.0.1:4280`; it blocks external network connections but allows same-origin requests for package integrity checks. `npm run dev:staging` starts connected mode at `http://localhost:3003` and loads Firebase Auth with the existing staging Web SDK config. It calls the staging Worker's `/v1/me` route and calls `/v1/clinic/workspace-role` only when a user explicitly confirms a role switch. Eleven app-specific first-party implementations are now in the role-filtered catalog and launch inside scripts-only opaque-origin frames through a nonce-bound `MessageChannel`: Treatment Protocols, Finance, Calendar, Treatment Progress, Work Entry, Patients, Appointments, Follow-ups, Staff, User Management, and Lab Tracker. Finance and Lab Tracker use the left module sidebar pattern from `abcd-repo` main. The Finance module formerly labeled “Transaction Record” is now labeled “Overview.” Work Entry and Patients have host-mediated media; Staff document media remains unavailable and fails closed in the Browser edition. These migrated apps have generated bundles and exact route policies, but they have not had authenticated workflow or visual acceptance. B5 workflow and visual acceptance remain open; B4 acceptance and its confirmed synthetic-data and cleanup gate for staging writes remain open.

The local shell is not an authenticated clinic workflow or app-runtime acceptance. The offline preview at `http://127.0.0.1:4280` intentionally makes no API calls and is not a staging CORS origin. The connected staging mode uses `http://localhost:3003`, which the existing Worker CORS policy allows. B1 and B2 made no SaaS source, Firebase configuration, Worker, or deployment changes.

Read-only staging review is recorded in [Architecture baseline](ARCHITECTURE.md). On 2026-10-28, the user-selected existing clinic Hosting site was updated to serve the Browser Edition. The local SaaS checkout had unrelated uncommitted changes, which were left untouched.
