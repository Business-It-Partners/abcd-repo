# Dental OS — Store and Cloudflare Distribution

**Baseline:** V1, 2026-10-15. Target architecture; implementation status is tracked separately.

Use a dedicated R2 release bucket separate from patient media/backups, and distribution routes in the existing Cloudflare backend. This is an extension to the SaaS platform, not a duplicate business service. No remote resources are provisioned by this documentation task.

## Control and delivery

The catalogue resolves approved app IDs, immutable releases, channels, platform/SDK/API compatibility, entitlements, withdrawn versions, and minimum-safe versions. Desktop checks metadata authenticity/freshness before selecting an install. Use signed metadata with expiry/sequence controls and a defined clock/error policy; HTTPS alone does not prevent replay of previously valid metadata.

User-directed milestone policy: the active staging App Store feed, update policy and immutable signed app packages live in private R2 bucket dental-app-distribution. The staging Worker serves authenticated catalogue, install policy, update policy and strictly shaped package responses; the desktop still independently verifies metadata freshness, package digest/signature, app identity, role/capability and update grants. New app package delivery does not use a public R2 origin. The former public staging release bucket remains temporarily available for older installed OS clients and rollback evidence; retire it only after a separately verified client migration. Production uses separate private resources and requires an explicit promotion task.

Immutable release objects are never overwritten. Downloads resume only when content identity remains the same. Enforce package size, storage reserve and concurrency limits. Catalogue outage must not silently delete working installations; known revocations/minimum versions and metadata expiry follow explicit fail-safe policy.

## Store UX

Show identity, company publisher, purpose, installed/available versions, capabilities, release notes, compatibility and operation status. Distinguish downloading, verifying, installing, ready, failed, update-ready and unavailable. Installation policy belongs to clinic/device administration; user business access still comes from Worker authorization. No third-party submission or app development portal exists.

## API namespace contract

New OS-specific routes use **`/v1/dental-os/...`** in the existing backend. Candidate contracts are:

| Candidate route | Purpose |
| --- | --- |
| `/v1/dental-os/catalogue` | approved first-party apps and compatible releases |
| `/v1/dental-os/releases` | release/version/channel metadata |
| `/v1/dental-os/download-intents` | authorized short-lived package downloads |

These names establish the namespace, not implemented endpoints or frozen HTTP methods/schemas. M07 freezes the detailed contracts; update metadata extends this namespace in M08. Publisher/control operations must have their own explicit authorization and cannot inherit clinic-user access automatically.

**Existing dental business and identity APIs keep their current routes and server authority.** Do not rename or duplicate them under `/v1/dental-os`. Desktop apps reuse them through the broker. A URL prefix organizes services; it does not isolate deployments, establish app identity, grant authorization, or protect production by itself.

This policy governs backend/distribution resources, not a claim that Windows/Linux installers can never be released. Local/staging release certification is allowed by its own implementation task; public/production publishing and production backend promotion remain separate decisions.

## M07 wire contract and local implementation

New GET routes are `/v1/dental-os/catalogue` and `/v1/dental-os/install-policy`; no query parameters or publisher mutation endpoint. Both resolve the existing Firebase/Worker clinic actor; install-policy returns exactly `{environment:"cloudfare-staging",canInstall:boolean}` and only clinic `admin` gets true. Doctor/reception users may read catalogue and use installed apps within ordinary business authorization. Transport/download visibility never confers installation or business permission. The additive backend patch is staged in a separate fewa_demo worktree, not deployed by documentation or CI.

Catalogue v1 is canonical JSON `{catalogue,keyId,signature}` using the same canonical serialization as dentalpkg/1. Ed25519 signs canonical `{purpose:"dental-os-catalogue",keyId,catalogue}`. Catalogue fields are exactly format 1, environment `cloudfare-staging`, channel `staging`, strictly positive integer sequence, issuedAt/expiresAt epoch milliseconds and at most sixty-four unique releases, matching the shared first-party app limit used by the catalogue and signed update policy. The local installed-app ceiling remains 16. Maximum body is 64 KiB; lifetime at most 24 hours; issue clock tolerance five minutes; expired metadata is rejected. Authenticated catalogue responses include x-dental-os-time epoch milliseconds from the live Worker; missing/invalid time or more than five minutes of device/server skew refuses selection. Verify expiry against the later server/local time, so rewinding the device clock cannot make an expired network catalogue fresh. Persist sequence, full-envelope SHA-256 and highest observed local time before enabling selection. Refuse lower sequence, changed bytes at the same sequence, and clock rollback beyond tolerance. Lost/corrupt watermark requires recovery; it is never silently reset. Metadata authenticity does not claim to defeat administrator deletion of all OS state.

Release fields are exactly id/title/description/version/notes/capabilities/platforms/sdkMajor/apiMajor/objectKey/packageSha256/packageBytes/payloadDigest/status/minimumVersion. Only platform-approved company IDs/key grants are accepted. SDK/API majors are 1, hosts Windows/Linux, versions follow dentalpkg/1, status approved/withdrawn; unsupported or withdrawn releases cannot install. Object key is exactly `releases/<id>/<version>/<wire-SHA256>.dentalpkg`. Signed catalogue binds full wire hash/size as well as dentalpkg payload digest; both are checked. No arbitrary URL, header, bearer token, disk path or script can be supplied by an app/renderer.

The main process constructs package URLs only from the signed object key. The active staging client sends package requests to the fixed authenticated Worker API with the main-owned clinic credential; it refuses redirects, limits bytes and total time, and reports download progress. The former public-origin transport remains available for older clients while the migration is verified, but the active staging configuration has no public package origin. Catalogue and policy use the fixed staging API and main-owned credential. Before registry activation, fetch fresh signed metadata and current admin policy again; refuse changed/withdrawn releases and stale session generations. One operation runs at a time; cancellation/session change stops before commit, no hidden resume/write queue. Ready follows registry success. Cache no patient facts or bearer tokens.

Normal Store uses trusted installed/catalogue state. Old Store simulation is retained only for private prototype regressions. M07 installs new apps; live update scheduling, full revocation/minimum-version launch enforcement, rollback and retention eviction remain M08. Running app lease blocks uninstall; user closes its shared window first. Catalogue failure never removes installations. Display installed fallback entries and safe status without provider URLs/tokens. At M07, the staging key authorized two company sample IDs and the public origin was not yet configured. M11 extends this to generic new `company.*` IDs from fresh signed catalogue/update policy within the platform-shipped company capability ceiling; third-party publishing and arbitrary sideload remain prohibited. The existing Cloudflare staging origin is pinned; `company.sample.preview` sequences 12–15 and evidence are recorded in M11. M12 presents trusted Store state in the shell; M13/M14 deliver Dental OS app packages; M20 certifies platform release operations.

**M15 signed update-policy evolution (ADR-026):** the existing purpose-signed update-policy envelope accepts format 1 for prior update-safety controls and additive format 2 for exact per-release API grants. Format 2 records bind up to six retained releases per app by version, package wire SHA-256, payload digest, and closed host API operation IDs. The app-level capability policy and platform-pinned company ceiling remain upper bounds. The current catalogue row must match the grant for the candidate release; retained fallback/trial versions require their own exact eligible record. The catalogue/update policy use the existing pinned company trust roots, environment, sequence, freshness and revocation rules. No new key, endpoint, publisher or policy-defined route is introduced. Format 1 grants no typed clinic API authority; details and implementation status are in [ADR-026](20_V1_ADR_REGISTER.md#adr-026--release-scoped-first-party-api-authority) and [SDK/broker contract](11_V1_SDK_AND_API_BROKER.md).

The operator prepares deterministic signed bundles outside the source tree with an external mode-0600 staging signing key, then validates release hashes before publication. Package object writes use atomic `If-None-Match: *`; matching existing bytes may be reused, collisions refuse. Catalogue replacement uses current ETag (`If-Match`) and a strictly increasing sequence; no blind pointer overwrite. No release private key is committed or shipped. The active staging package publisher writes to the private app bucket; the former public staging bucket is retained temporarily for older clients and rollback evidence, and contains no patient data or credentials. [Cloudflare public bucket policy](https://developers.cloudflare.com/r2/buckets/public-buckets/) limits r2.dev to non-production use; [conditional writes](https://developers.cloudflare.com/r2/api/s3/api/) provide atomic object creation/pointer guards. Staging signing key rotation requires a reviewed platform trust update, higher catalogue sequence and explicit operational authorization; unsupported keys fail closed.

Staging samples request platform-local capabilities only; appointment read/write grants are excluded until M09's actual SaaS integration proof. Their workflow UI stays explicitly synthetic. Private legacy SDK fixtures retain their controlled synthetic API behavior. No live business operation is exercised as part of M07 package delivery.

## Private distribution implementation — staging, 2026-10-26

The existing Cloudflare staging Worker binds dental-app-distribution for signed app feed/packages and dental-os-distribution for the Windows preview installer. Both buckets remain private with public r2.dev access disabled. The initial sequence 108 feed and all 11 package objects were copied byte-for-byte. On 2026-10-26, the signed catalogue advanced to sequence 110 with only Follow-ups 1.0.5; its signed update policy retains the existing grants for all 11 apps so already-installed apps on other devices keep their API access. The other ten package objects were removed from dental-app-distribution. The package publisher writes future signed releases to the private app bucket using temporary nonce-protected Workers and conditional R2 writes. Artwork remains on the existing separate artwork bucket and uses its bounded Worker route.

The app package route requires the same authenticated clinic identity as catalogue and update-policy routes. The Windows preview download route exposes one fixed installer key through the staging Worker for the local demo website. That artifact is unsigned and does not complete M20/G20/G21 or production release certification. No production config, branch or bucket is changed.
