## ADR-023 — Signed first-party app onboarding within the shipped company trust ceiling

**Decision:** The platform does not keep a per-app allowlist that must change for every new company app. A currently pinned company publisher key may register a new `company.*` app ID through the fresh, signed staging catalogue and matching signed update policy. The platform ships the company publisher trust root and a bounded maximum capability set; each release and update policy carries the exact app capability grant, and the verifier rejects any grant outside that platform ceiling. Catalogue, policy, package, registry, and runtime identity must match. The package cannot supply an ID authorization, capability, key, origin, preload, or native code.

**Tradeoff:** An approved company signing key can onboard new first-party IDs without an Electron release, while compromise of that key could authorize an app within the shipped company capability ceiling. Revocation, expiry, sequence freshness, minimum versions, and digest/key revocation remain signed controls. Adding a capability outside the ceiling still requires a trusted platform policy/release change. This does not create third-party publishing, arbitrary sideloading, or a public extension API.

**Evidence and limits:** Linux tests cover the generic runtime and Store path; Cloudflare staging sequences 12–14 demonstrate `company.sample.preview` `1.0.0` → `1.1.0` → `1.2.0`, with sequence 15 publishing 1.3.0. Authenticated clinic Store install/update service acceptance and a private live-feed desktop install/update/restart pass are recorded in [M11 evidence](../dental-os_v1_working_info/milestone-11-flexible-first-party-app-updates/VERIFICATION_EVIDENCE.md). The user reports completing the manual 1.3.0 desktop update. Local failure/recovery tests and final-source Windows CI pass. The 16 minimal synthetic apps measured 2.09 GiB peak aggregate working set across 20 processes; closing all app views returned the shell to 487 MiB across four processes. This is a working-set sum with no enforced budget, not PSS or proof for clinical workloads/low-memory devices. M11 closes G11 for its recorded scope; this does not certify Windows release operations (M20/G20) or final device acceptance (G21).

## ADR-026 — Release-scoped first-party API authority

**Decision (2026-10-22):** a first-party app release receives only the closed host API operation IDs explicitly granted to that exact package version and digests by the existing company-signed catalogue/update-policy authority. Use the already pinned company trust roots, signature purpose, freshness, sequence, revocation and environment controls. Do not introduce an API-specific signing key, trust root, endpoint, route manifest, app-to-app message or intent system.

The additive update-policy format 2 carries up to seven exact release records per app: semantic version, package wire SHA-256, package payload digest and operation IDs. The signed app-level capability list and platform/company trust ceiling remain ceilings. The catalogue's current release must match the corresponding format-2 identity. Retained eligible trial/known-good/fallback versions use their own exact records; no version borrows a successor's grant. Format 1 remains usable for its prior update-safety purpose but authorizes no typed clinic API operation.

The initial closed API catalogue contained `appointments.list` and `appointments.setStatus`. ADR-027 subsequently defines the host-owned clinic JSON contract for `clinic.api.request`; it still requires an exact signed release grant and precise local route/session validation. `clinic.api.blob.read` remains denied without a later explicit media contract. These decisions approve no new Worker routes or business schema semantics. Session/Worker authorization remains authoritative; renderer code receives no credentials and cannot select a tenant, role, absolute URL or headers. JSON path/method selections resolve only within the versioned host-owned contract.

SDK/API major 1 remains compatible for an app-only release that selects an operation already defined by the host. A new operation contract, route, schema or security/business semantic requires explicit platform/API compatibility review and its own host release before any package grant can name it. First-party catalogue onboarding remains bounded by platform trust and capability policy under ADR-023.

**Tradeoff and migration:** release-scoped records permit approved app-only capability evolution without updating the desktop, at the cost of signed policy growth and retaining grants for every eligible local release (bounded to seven). The bound was raised from four to six on 2026-10-23 so Patient Record and Treatment Protocols could preserve six exact release grants. It was raised from six to seven on 2026-10-23 so Patient Record, Treatment Protocols and Treatment Progress can each add their next release without removing any eligible fallback or trial grant. Hosts enforcing an earlier four-, five- or six-record bound reject the new signed policy until they receive a platform build with the updated validator. Format-1 policy fails closed for API calls during migration. If an exact record is absent, expired, revoked, mismatched or outside the platform ceiling, that release receives no API authority; safe update/fallback policy remains independently enforced.

**Scope/evidence:** the user selected the existing signed company catalogue/update-policy authority on 2026-10-22. M15 integrates the format-2 verifier/resolver and synthetic positive/negative tests for a previously unlisted first-party app and a v1→v1.1 API-only grant extension on the same host implementation. See [M15 verification evidence](../dental-os_v1_working_info/milestone-15-platform-closeout-and-integration/VERIFICATION_EVIDENCE.md). Final combined-source verification, M17's per-app route inventory, media, navigation, and payload needs remain tracked separately; this ADR alone does not close G15 or authorize a new route.

## ADR-030 — OS-owned local file acquisition, Files, and recipient-bound receipts

**Decision direction (2026-10-22):** Dental OS provides a read-only Files core system window, a common OS-owned custom picker and a parented native host picker fallback. Trusted Electron main mediates local host filesystem access. A company dental app may request only an approved user-gesture-controlled selection, receiving an opaque, short-lived, release/window/session-bound receipt and no raw path or Node access.

**Options:** requiring host file explorer alone causes fullscreen friction; each app building its own explorer duplicates privileges and UX; generic fs SDK access is forbidden; OS-owned read-only service and picker is selected. The Files UI is system owned, not a dental package elevated beyond its declared privileges. A drag gesture is preferred but not assumed reliable across WebContentsView; explicit user-directed Send to an eligible app is mandatory fallback.

**Compatibility and safety:** Existing M15 signed format-2 clinic API grants do not authorize local filesystem access. Implement a distinct, versioned local selection contract guarded by verified company package, platform trust ceiling, explicit user action and current session; choose exact signed metadata/release policy representation under M16.1 before implementation. Preserve ADR-013/R13 no general app messaging, sandbox/context isolation, OS path/ACL/symlink safety, revocation and non-persistence of patient content.

**Owner and proof:** M16/G16. [Architecture](../dental-os_v1_working_info/milestone-16-file-acquisition/ARCHITECTURE.md) and [Plan](../dental-os_v1_working_info/milestone-16-file-acquisition/PLAN.md). New code, local drag semantics, host permission handling, Windows/Linux focus and resource behavior require source-bound acceptance. No Cloudflare upload, business record association, file modification, staging/production deployment or G16 completion is implied by this ADR.

### M16.1 contract resolution (2026-10-22)

After inspecting the M15 source, M16 selects a distinct SDK local operation `local.files.pick` (candidate minor 1.5). A current signed app manifest, fresh company-signed **app-level capability** in existing update-policy metadata, platform company ceiling, approved clinic app-family session and exact registered WebContents/frame/release are all required. The existing format-2 **clinic API** release-grant list is unchanged and cannot grant local host file permissions. In particular, the current default local-operation authorization path in SessionManager must never be sufficient to open files.

The trusted app preload observes genuine `isTrusted` pointer/keyboard activation and registers a short-lived, single-use, main-process activation ticket (750 ms). Caller-provided gesture booleans/nonces are refused. Actual file access additionally requires explicit user choice in the **OS-owned picker** or parented native open dialog. The app gets only a short-lived, one-recipient metadata receipt; no host path, file bytes, generic read/write/execute permission or media upload.

Read-only OS Files uses main-process rooted, opaque folder IDs and paged listings; the shell owns the Files window and Send destination. Files-to-app is a platform-mediated selection receipt, not a general app-to-app messaging bus. Explicit Send remains mandatory. The 2026-10-22 source/API review found the current one-visible-native-input-surface runtime cannot attest the actual recipient while Files is foreground; native cross-WebContentsView drag is formally deferred for this architecture. No drag access, raw path, or IPC was added, and existing authorization/isolation/receipt behavior is unchanged. This is an unresolved G16 scope decision, not gate acceptance. Physical-device walkthrough is NOT RUN. See [M16 architecture §15](../dental-os_v1_working_info/milestone-16-file-acquisition/ARCHITECTURE.md) and the [device handoff](../dental-os_v1_working_info/milestone-16-file-acquisition/DEVICE_ACCEPTANCE_HANDOFF.md). G16 remains OPEN until physical cases pass and the agreed drag disposition is recorded.

**Files UI follow-up:** the image-first grid uses standard folder/type icons and bounded previews only for supported raster picture files. A shell-only `files:thumbnail` path returns at most 16 MiB of source bytes to the sandboxed OS shell renderer for validation and reduction to a transient 256 × 192 thumbnail; dental apps still receive metadata-only receipts and have no thumbnail/file-byte API. Nothing is persisted or captured into the overview/minimized preview. The exact rules and limits are in [M16 architecture §16](../dental-os_v1_working_info/milestone-16-file-acquisition/ARCHITECTURE.md). This UI contract leaves authorization, sandbox boundaries, explicit Send and the drag deferral unchanged; hosted and physical acceptance remain separately recorded.

## ADR-031 — Device-persistent session after sign-in

**Decision (2026-10-23):** at the user's direction, a successful desktop sign-in automatically saves only its refresh token using the existing native protected-storage provider. On startup, show the Sajilo Dental splash while restoring that token and rechecking Firebase and Worker `/v1/me` authority; open the workspace only after current clinic access is resolved. Remove the remember-device/session checkbox. A normal app close preserves the protected session; sign-out/switch-account clears it. The existing explicit Lock action continues to clear the saved token and require sign-in, so a deliberate lock cannot be silently bypassed on next launch.

**Failure behavior and tradeoffs:** if supported protected storage is unavailable or save fails, keep the current session usable, clearly say it lasts only for that app session, and never store credentials in plaintext. Persistent sign-in reduces daily friction while relying on the host account/keyring for device access; users on shared devices can explicitly Lock or Sign out. Passwords and ID tokens are never persisted. Refresh-token rotation and existing revocation/Worker authorization checks remain authoritative.

**Alternatives:** retain opt-in remember-device/session (rejected because users must repeat an unnecessary choice); persist a password (rejected); or make every session temporary (rejected because reopening the desktop should not require another email/password entry).

**Implementation scope:** this change removes the `remember` field from shell login IPC and makes SessionManager attempt the existing encrypted refresh-token save after every successful login/renewal. It adds no auth provider, backend route, local business database, or offline write queue. The original M05 decision/evidence remain as historical proof of the prior optional flow. Implementation is local to `codex/m15-auth-session`; build and private launch evidence are recorded separately, with M15/G15 acceptance still open.

## ADR-032 — Remember sign-in email separately from session persistence

**Problem:** after sign-out or session expiry, entering the email on every sign-in adds friction. Remembering a sign-in identifier must not weaken or change the protected session policy in ADR-031.

**Decision (2026-10-23):** the sign-in form shows a default-checked **Remember me** checkbox. When enabled, the renderer stores only a validated email address in the local app profile and prefills it on a later sign-in. When disabled, it immediately removes the saved email; while unchecked, sign-out/lock clears the current form email too. The preference is local to the app profile and does not opt into session persistence. Sign-out and Lock continue to clear saved refresh credentials under ADR-031.

**Options and tradeoffs:** leaving the email blank avoids profile storage but requires retyping it; remembering a password or changing the protected-session choice is rejected. Remembering the email is selected at the user's request because it removes repetitive typing without persisting an authentication secret. It remains readable to the same local app-profile user and is not represented as protected credential storage.

**Contracts and recovery:** no `LoginInput`, preload, IPC, Firebase or Worker contract changes. Passwords, ID tokens and refresh tokens are never stored by this preference. If local renderer storage is unavailable, the checkbox still works for the current window and sign-in remains available; malformed/oversized stored email is ignored. The user can uncheck at any time to delete the saved email.

**Owner and proof:** M15 local sign-in UI. Record build and visual evidence in the milestone status; M15/G15 acceptance remains separate and open. No backend, production, commit or push change is implied.

## ADR-034 — Two-open-app limit for V1

**Decision (2026-10-25):** the V1 desktop permits no more than two managed app windows to be open at once. Any lifecycle phase other than `closed`, including minimized and transitional phases, counts as open. If a user tries to open a third app, the OS leaves it closed and presents a blocking OS-owned dialog listing the open apps and asking the user to close one before retrying.

**Behavior and tradeoffs:** the user chooses which app to close; the OS does not auto-close an app or introduce an idle/freeze state. Existing in-flight API requests are not cancelled by this limit. The small fixed cap is a V1 resource-use measure, not a measured RAM ceiling or a claim that active app work is suspended.

**Owner and proof:** M15 shared window manager/runtime. The local `codex/clinic-logo-fix` candidate implements the reducer guard, dialog, shell inertness and native-surface hide path. Build and documentation validation are recorded in the M15 candidate notes; M15/G15 acceptance remains open. See [Shell and Desktop](06_V1_SHELL_AND_DESKTOP.md) for the target contract. No automatic eviction, API permission, backend change, publication or release follows from this decision.

## ADR-035 — Separate source-only development app lane for first-party M17 apps

**Problem:** app iteration should not require rebuilding a signed package and publishing it to the Cloudflare App Store. A developer build must also never replace or share the installed release files or app profile.

**Decision (2026-10-25, revised):** a locally run, unpackaged Dental OS checkout shows a center-left grid for the ten fixed first-party M17 apps. Developers build each app with its own project workflow and explicitly publish its bounded output into an immutable snapshot under the OS user-data `development-apps/` root, with an independent `registry.json`. Selecting a tile reads the active snapshot; the OS does not import a checkout's `dist` during launch. Released packages and their signed registry remain under the separate `packages/` root. The dock resolves only released packages; the development grid resolves only local development snapshots. There is no fallback between the two channels, and a development version does not need to match or be installed from the Store. Each channel keeps a distinct runtime ID, origin and Electron session partition. The current app business records remain in Dental SaaS; no local clinical database or offline write queue is added. See [ADR-036](#adr-036--separate-browser-and-dental-os-preview-lanes-with-a-shared-development-bucket) for the shared publisher and Browser Preview contract.

Local development manifests are checked against a fixed per-app development capability grant. The existing broker still enforces clinic identity, role, app-family route rules and capability checks. Development capability changes require an explicit change to the host's development grant; ordinary app code and version changes do not. Reopening a running development app uses the shared close guard for unsaved work and unresolved server writes. A local import changes neither the signed Store registry nor a Cloudflare object. App releases continue through the normal signed, versioned Store workflow after review.

**Boundary and tradeoffs:** this lane is available only when Dental OS runs from its source checkout and is absent from packaged builds and staging, except a guarded private UI fixture. The renderer supplies only a fixed app ID; it cannot select a path, command, executable or permission. The OS validates app identity, compatibility, local capability grants, bounded files and the snapshot digest before launch. Local development artifacts are same-user files and are not represented as company-signed releases.

**Alternatives:** publish every edit to Cloudflare (rejected for iteration because it adds packaging and publication overhead); reuse the installed signed package directory with a version switch (rejected because it mixes release and development storage); allow arbitrary folders or unsigned apps (rejected because it creates a sideload path); or ship app source/build tooling in the clinical OS (deferred because it expands the installed product's executable/tooling surface).

**Owner and proof:** M15 source-run developer workflow. The implementation and private verification record are in [M15 status](../dental-os_v1_working_info/milestone-15-platform-closeout-and-integration/STATUS.md#local-development-app-collection--2026-10-25). This does not close M15/G15, authorize publication, or make a claim about a packaged OS build.

## ADR-036 — Separate browser and Dental OS preview lanes with a shared development bucket

**Problem:** developers need a fast source preview without clinic credentials and a separate OS preview that exercises the real host session and API broker. Builds from multiple app worktrees must update the same device-level development store without replacing other apps or mixing with signed release storage.

**Decision (2026-10-25):** Browser Preview runs one first-party app from source with Vite/HMR, synthetic session/data, disabled clinic writes and native file selection, and a restrictive local-only connection policy. Dental OS Preview uses an explicit build-and-publish command; the OS itself reads only validated immutable snapshots from `<Electron userData>/development-apps/`. That bucket has its own registry and snapshot tree, is shared by app worktrees using the same OS profile, and serializes pointer updates so publishing one app preserves every other app. The publisher reuses the existing bucket and creates it in the canonical user-data location only when absent. Release package storage, signatures and Cloudflare publication remain separate.

On a new launch, the OS resolves the app's current active development snapshot. A running app retains the exact snapshot it started with; selecting its tile focuses that instance. After a new publish, close and reopen only that app to load the update, with the normal unsaved-work and uncertain-write close guards. This workflow does not require an installed signed app to share its version or permissions. The platform's fixed first-party catalog and development capability grant remain authoritative, and the real Dental OS broker/session remains authoritative for OS Preview.

**Release gate:** source changes and local development snapshots remain unbundled unless the user explicitly requests a release bundle. A release still requires the normal signed, versioned Cloudflare App Store workflow. Browser or OS preview is not release evidence or production acceptance.

**Owner and proof:** M15 source-run developer workflow. Code and evidence status are recorded in the [M15 status](../dental-os_v1_working_info/milestone-15-platform-closeout-and-integration/STATUS.md#two-preview-lanes-and-cross-worktree-publishing--2026-10-25). The implementation does not close M15/G15 or publish any release.
