# Dental OS — dentalpkg/1 exact package and local transaction contract

**Frozen:** M06, 2026-10-16. Ed25519 + SHA-256; implementation/evidence remains in the milestone record. This format carries company web assets only.

## Bytes and signature

A `.dentalpkg` file is canonical UTF-8 JSON with exactly `payload`, `release`, `signature`. No BOM, whitespace, duplicate keys, alternative base64 spelling or extra keys. Objects sort keys by JavaScript UTF-16 lexical order (schema keys/paths are ASCII); arrays preserve order; strings use JSON.stringify escaping; numbers are nonnegative safe integers in decimal. Canonical round-trip equality is required. No Unicode normalization is performed; metadata uses constrained ASCII identifiers and paths.

`payload` is standard padded base64 of canonical JSON `{manifest, files}`. `release` has exactly `format:1`, `appId`, `publisher`, `version`, `digest`, `keyId`. `digest` is lowercase SHA-256 of the decoded payload bytes. `signature` is padded base64 of the 64-byte Ed25519 signature over canonical release bytes (no prehash). Key IDs identify platform-owned Ed25519 public keys; a signature never supplies its own trust key. Release identity/publisher/version must exactly match the manifest. The canonical payload digest binds every manifest field and asset byte. There is no circular hash or detached unsigned metadata.

Manifest keys: `format:1`, stable `appId`, `publisher:"company"`, numeric three-part `version` (each component 0..9999; no leading zero), relative `.html` `entry`, `sdkMajor:1`, `apiMajor:1`, unique known SDK `capabilities`, and `assets`. Each inventory entry has exactly `path`, byte `size`, lowercase `sha256`. Inventory is strictly ascending path order. `files` is an identically ordered array of exactly `{path,data}`; data is padded base64. Every inventory/file must match exactly; entry must be inventoried. SDK/API major mismatch and capability requests exceeding the platform's company-app policy fail closed. API major 1 means the M04 staging broker contract, not arbitrary app-selected endpoints.

## Portable archive limits

This is deliberately an uncompressed container rather than ZIP/TAR. It has no link, mode, special file, compression or executable-hook representation. Unknown fields/types are rejected, even if signed. The outer file is at most 16 MiB; decoded payload at most 12 MiB; total assets at most 8 MiB; individual asset at most 2 MiB; 128 files; 160 ASCII characters/path; eight path components. The builder and verifier enforce the same limits. Base64 overhead is a tradeoff for a small, deterministic, dependency-free V1 parser; large imaging datasets are not package assets.

Paths use lowercase ASCII letters/digits, `.`, `_`, `-` and `/`; start with an alphanumeric character. Reject empty/dot/dot-dot components, absolute/drive/UNC paths, backslashes, percent escapes, Windows devices, ADS, trailing dots, duplicates, case aliases and file/parent conflicts. Allowed extensions: html, js, css, json, svg, png, jpg, jpeg, webp, woff2. Web JavaScript runs only in the platform sandbox; a bundle can never supply its own preload, Node/native execution or install script.

## Trust and launch binding

M06 normal platform policy was empty/fail-closed. M07 prepares separate staging company sample trust; its public origin stays unconfigured until approved rollout. Production release trust remains empty. No production signing private key is created in M06. Only the guarded private Linux display or GitHub Windows test profile can load the separately signed sample fixtures. Their ephemeral signing key is discarded; only public key and bundles are retained. Local fixture success does not approve a production signing workflow or remote release freshness (M07).

Registry lookup selects the platform-owned app ID and digest. At each launch, verify envelope/signature/compatibility and all installed bytes, reject missing/extra files/directories and links/hardlinks/junctions. Bind actual webContents/main frame/own origin to the verified ID/version/grants. Serve a bounded, pinned in-memory copy with platform CSP, no direct network and no file URL exposure. Mutable disk changes cannot replace bytes in an existing instance; the next launch rejects tampering. This does not protect against an administrator, patched host executable or fully compromised same-user account.

**M15 API authority:** the package manifest remains `dentalpkg/1`; it contains only an SDK capability ceiling and does not carry route authority. Under [ADR-026](20_V1_ADR_REGISTER.md#adr-026--release-scoped-first-party-api-authority), clinic API operations are granted by format 2 of the existing signed update policy, not by a package signature or app-wide capability alone. Each grant binds the verified manifest/release version, full wire-package SHA-256 and payload digest to closed host operation IDs. The current catalogue candidate must match the grant; eligible retained versions use their own exact records. Format 1 grants no API operations. A changed API route/schema or new operation still requires a platform compatibility decision; metadata cannot define one.

## Local state and crash semantics

Actual root is `<Electron userData>/packages/`: `registry.json` format 1, `operation.json` format 1, `operation.lock`, `staging/<uuid>/`, `apps/<company-app-id>/<payload-digest>/`. Each immutable version contains `bundle.dentalpkg` plus inventoried assets. No patient records, auth credentials, arbitrary destinations or package-chosen disk state. New schema versions require explicit migration; unknown schema/corruption preserves files and demands recovery rather than resetting installs.

One trusted host owns the profile (Electron single-instance lock); all package mutations/launch verification additionally acquire an exclusive operation lock. No worker extracts concurrently. Bootstrap alone may remove a lock whose recorded PID is conclusively dead; live, malformed or uncertain ownership refuses recovery. This is single-host ownership, not distributed filesystem locking. Atomic file replacement uses exclusive temporary files, file fsync, rename and POSIX directory fsync; Windows relies on Node/NTFS replacement semantics and needs the deferred physical power-loss/storage checks. Never claim process-exit tests simulate a sudden physical power failure.

Install verifies first, checks free capacity for bundle+expanded assets+4 MiB headroom, journals intent, extracts regular files in a unique staging directory, revalidates, renames to an immutable version, then atomically commits the active registry pointer. Failures before registry commit preserve the old pointer. Startup removes journal-owned staging/unregistered versions; a committed pointer wins. Recognized abandoned root atomic-write files are bounded and reclaimed. EIO/ENOSPC preserves a recoverable journal; inability to safely clean up remains an explicit recovery error. Capacity is checked, not an exclusive filesystem quota.

At most 64 first-party apps and three versions per app are retained. Equal-version replacements/downgrades and historical reactivation are refused; active identical installs are idempotent. M08 owns controlled eviction/rollback/revocation and user timing. A live lease pins bytes and blocks uninstall. Uninstall journals, unregisters atomically, then deletes only that app subtree; interrupted deletion is retried at startup. Interrupted before unregister leaves the install. Unsafe linked cleanup paths are preserved and reported, never followed. SaaS records and other app directories are outside deletion ownership. M07/M08 will wire these primitives to actual Store truth; the existing synthetic Store is not converted in M06.
